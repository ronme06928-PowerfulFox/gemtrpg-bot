## 読む前に

この文書はGM・シナリオ制作者のアプリ操作を扱います。ゲームルールは[基本ルールブックの案内](../../typst_manual/全体マニュアル/README.md)、PLの操作は[A01](A01_Player_Manual.md)を参照してください。目的別の入口は[START_HERE](../START_HERE.md)です。

通常ルームでは、1章で準備し、2章で戦闘を進めます。3章は進行中の介入・復旧、4章は素材・プリセットの制作です。アプリ管理者の設定・デプロイ・内部APIは[F01](F01_Operations_Manual.md)に分離しています。

本再編はコード・仕様照合によるものです。PL側からのGM進行確認は台帳§15〜16、GM自身による通常ルーム作成→招待設定→突入→代理宣言・解決→終結→成果代理反映のブラウザ確認は§18に記録しています。素材制作・戦闘専用など、ブラウザ未確認の経路も同節で分けています。項目別の移動先・根拠は[出典・不足台帳§17](../planned/46_Publication_Source_Inventory.md)を参照してください。

基本ルールブックは第0〜7章と巻末を収録しています。第8章は保留で、詳しい世界観と旧作例は[旧ルール本](../../typst_manual/全体マニュアル/旧版/旧ルール本.typ)に保持しています。

## 1. 卓を準備する

### 1.1 ルームを作成してGMとして入室する

ロビーから通常ルームの「＋ 新規ルーム作成」、または「戦闘専用ルーム作成」を選び、ルーム名と4桁数字のGM PINを指定します。作成者はownerになります。GM PINは参加コードとは別です。

参加済みルームは「入室」から開きます。owner/gm membershipを持つ場合はサーバーがGM権限を判定します。playerがGMとして入る場合には、有効なGM PIN（または管理用マスターキー）による認証が必要です。アプリ管理者は仮想ownerとして入室できます。入室画面の選択とDB上のロールは別なので、PIN入力だけを権限判定の全条件とはしません。

| 権限 | 主な操作 |
| --- | --- |
| owner | 画面では公開設定・説明・募集状態・参加コード。メンバーのGM付与/解除・除名・owner移譲はAPIのみ |
| gm | ルーム内の戦闘進行・代理操作、募集状態の変更 |
| player | 自キャラ操作、チャット、状態閲覧。戦闘専用ルームには別の進行権限あり（2.6） |
| アプリ管理者 | 全ルームでowner相当。アカウント管理はアプリ全体の別権限（F01 Part 1-B） |

ロビーへ戻ってもmembershipは残ります。一時的なルームGM状態の解除と、gm membershipの削除は別です。表示名変更とパスワード変更はロビーのユーザー設定から行います（[A01 §1](A01_Player_Manual.md#1-始める前に)）。マスターキーの環境変数・初回管理者設定はF01 Part 1-Bで扱います。

### 1.2 参加者を招待する

ownerはロビーの「⚙️設定」、またはルーム内のユーザー設定からルーム設定を開きます。gmが変更できるのは募集状態です。

| 公開設定 | 未参加者への表示・参加 |
| --- | --- |
| 非公開（hidden） | 一覧に出さず、新規参加を受け付けない |
| 公開（listed） | 一覧に表示し、新規参加を受け付ける |
| 締切（closed） | 一覧には表示するが、新規参加を受け付けない |

参加済みの人は非公開・締切でも一覧から再入室できます。募集状態の自由入力欄と、この公開設定による参加可否は別です。

- 「設定 / 再発行」から参加コードを指定します。4〜32文字で、空欄なら自動生成します。
- 設定・再発行時だけ実値が表示されます。新しいコードを発行すると前のコードは使えません。
- 「失効」はコードを削除する操作です。**公開ルームでコードがなくなると、コードなしで新規参加できます**。新規参加自体を止めるには公開設定を非公開または締切にします。
- メンバーへのGM付与/解除、除名、owner移譲はowner/アプリ管理者用APIにありますが、現行の画面には操作する入口がありません。owner移譲APIの実行後、元のownerはgmになります。画面のルーム設定・参加コードもアプリ管理者はowner相当で扱えます。
- GM PINを入力して入室したplayerはgm membershipへ昇格し、退出しても自動でplayerへ戻りません。参加者へは参加コードを伝え、GM PINは共有しません。

ルーム削除ボタンはowner/アプリ管理者に表示されます。管理者以外の画面操作ではGM PIN等の削除認証も求められます。サーバーもowner membershipを検証します。owner以外のGM・playerは、有効なPINを知っていても削除できません（D15、作業B7）。

### 1.3 キャラクターと盤面を準備する

ドックの「➕」から味方・敵を追加し、「📦」の未配置一覧から配置します。未配置のキャラクターは行動順・未行動確認・PvE自動行動の対象外です。自分のキャラクターはPL自身でも配置できます。

通常ルームの「通常プリセット」は、プリセット配置画面から素材や編成を選ぶ入口です。プレビューで追加・置換などの変更を確認してから適用します。従来の「敵一覧保存」は別の補助機能で、現行の資産管理・環境間移送と区別してください。配置・制作の仕様は[E02](E02_UI_Component_Specs.md)と4.3を参照します。

背景・立ち絵は画像ピッカーで登録・選択します。画像の扱いは1.4、戦闘専用ルームの配置は2.6で扱います。

### 1.4 画像を登録・選択する

画像ピッカーの「新規アップロード」でファイルを選び、必要なら名前を付け、アップロードが成功すると、その画像がそのまま選択されます。必要に応じてトリミングを経由します。

- 対応はPNG/JPEG/GIF/WebP、10MB以下です。SVGは使えません。
- GM限定にする場合は、アップロード時に「🔒 GM限定画像として保存」にチェックします。この欄はGMにだけ表示されます。
- 公開範囲は`public`と`gm`です。GM専用画像を一覧で扱うにはGM状態である必要があります。PL状態での自分のアップロードも例外ではありません。
- 拡張子・MIME・内容検証、Cloudinary設定とエラーの調査手順はF01 Part 1-Cに保持しています。

### 困ったとき（準備）

| 症状 | 確かめること |
| --- | --- |
| PLからルームが見つからない | 初参加なら公開設定を公開にしたか。既存メンバーの再入室とは区別します |
| コードを失効したのに新規参加できる | コードなしの公開ルームは参加可能です。公開設定を非公開または締切にします |
| GMの操作が出ない | 正しいアカウント・ルームでGMとして入室したか。アプリ管理者とルームGMを区別します |
| GM専用画像が一覧にない | 現在GM状態か。形式・サイズ・アップロード失敗はF01 Part 1-Cを参照します |

## 2. 当日のセッションを進める

### 2.1 探索・戦闘の画面とルーム種別

探索画面と戦闘画面の切替、通常ルームと戦闘専用ルームの種別、PvE/PvPの戦闘処理はそれぞれ別です。探索ドックの「⚔️」（戦闘パートへ戻る）で通常ルームの戦闘画面へ切り替えただけでは「戦闘突入」になりません。宣言後の「⚔️」（戦闘開始）は別の操作です。

探索判定はシナリオに従い、GMが技能・ダイス数・必要なら目標値を案内します。ダイス数は1個固定ではありません。PLの入力手順はA01 §4.6、裁定は台帳D03です。

### 2.2 通常ルームで戦闘を始める

1. キャラクターの追加・配置と、今回の資源・状態を確認します。
2. GMが「戦闘突入」を押し、確認します。表示が「戦闘中」になります。
3. 右側の戦闘コントロールで「R開始」を押します。ラウンド開始・速度処理後、駒の上にスロットが表示されます。
4. PLがスキルと対象を選んで宣言します。GMは全キャラクターの代理宣言ができます。
5. 全スロット確定後、GMが戦闘パートの選択フェーズに表示される「⚔️」（戦闘開始）を押して解決を開始します。通常ルームではPLが押してもサーバーが拒否します。

R開始・R終了はGM・通常ルーム・戦闘中の条件で表示され、探索パートでは非表示です。前ラウンドの終了処理が未完了ならR開始は拒否されるため、先に「R終了」を行います。

HP・MP・FPは戦闘突入のたびに全回復・FP0へ初期化するルールではありません。シナリオで回復などの指定があればGMが案内します。計算・マッチ・広域等のゲームルールは基本ルールブック、内部の処理順は[B03](B03_SelectResolve_Spec.md)を参照してください。

### 2.3 解決の表示を進める

宣言を確認してGMが解決を開始します。解決パネルでは威力のレンジと実際の威力、勝敗、ダイス由来・効果由来ダメージを確認できます。

- 解決表示は共有され、**進行役（通常ルームでは「⚔️ 戦闘開始」を押したGM）**が「次のマッチへ」で進めます。
- 「表示後2秒で自動進行」を有効にすると、表示後に次の処理へ進みます。
- 進行役でないGMは、現在の進行役が在室していても、いつでも「進行役を引き継ぐ」を使えます。通常ルームのPLにはGMと同じ引き継ぎ権限はありません。
- 解決表示中はログを段階的に反映します。最後の表示まで進むとラウンド終了処理を行います。独立した「まとめ結果」の欄が必ず出るとはしません。

次ラウンドはGMが「R開始」で始めます。「R終了」による介入は3.3で扱います。対象のスロットが存在しない場合や権限不足の宣言はサーバーが拒否します。代理操作でも、画面のスキル・対象・確定状態を確認してください。

### 2.4 戦闘を終結する

GMが「戦闘終結」を開き、`VICTORY`・`DEFEAT`・`RETREAT`・`INTERRUPTED`から結果を選んで確定します。未解決の内容がある場合は、破棄の案内を確認します。

- 終結後は「戦闘準備中」へ戻り、次の遭遇をラウンド1から始められます。
- HP・MP・FP・盤面配置・召喚体は保持されます。宣言・マッチ・行動順、ラウンド制の状態、伝授スキル、行動済み等の一時情報はクリアされます。
- 「戦闘記録」では結果・開始終了時刻・完了ラウンド・参加者別ダメージを確認できます。参加者名は当時の記録なので、後のキャラ削除で消えません。
- 初期参加者は突入時に配置済みの通常キャラクターです。召喚体のダメージは所有者に集約し、所有者不明分は「その他の召喚体」と表示します。
- GMは戦闘記録を1件または全件削除できます。削除は復元できません。

### 2.5 報酬を反映して退出する

持ちキャラ由来のキャラクターは詳細の「⚙」から経験値とアイテムを反映できます。GMは持ち主に代わって反映できます。報酬を決めてから入力し、成功ログと設定メニューの反映済み表示を確かめます。

ルーム内コピーごとに1回だけです。経験値0でも反映済みになります。JSONを直接貼り付けたキャラは対象外です。入力形式とPL側の手順は[A01 §5](A01_Player_Manual.md#5-セッションの後)、内部仕様はF01 Part 9にまとめています。保留中のモードの条件分岐を通常セッションの手順へ持ち込みません。

「🏠」からルーム一覧へ戻っても、参加資格とルーム内キャラクターは残ります。アカウントのログアウト、戦闘終結、成果反映、リセットは別の操作です。

### 2.6 戦闘専用ルームの別経路

通常ルームの「戦闘突入／戦闘終結」と「R開始／R終了」は戦闘専用モードでは使いません。戦闘専用編成・ステージ選択・配置から専用の開始経路へ進みます。

- 素材の閲覧・編集権限と、ルームへの配置権限は別です。配置はルームのowner/gmが行います。
- 解決表示の進行役が不在のとき、戦闘専用ルームではPLも引き継げます。サーバー側には通常ルームとは異なる終了・リセットの権限があります。
- 共通手順へ一律に「GMのみ」と書かず、[D01 Part 2](D01_Play_Mode_Specs.md)と[E02](E02_UI_Component_Specs.md)の専用手順を参照します。GM側の画面通し確認は4Fで行います。

### 困ったとき（進行）

| 症状 | 確かめること |
| --- | --- |
| R開始・R終了が出ない | 通常ルームで、GMとして入室し、戦闘突入した後か |
| 解決表示を進められない | 進行役か。GMなら引き継ぎボタンを確認。戦闘専用の不在時は2.6 |
| 宣言できない・カードを選べない | A01の4章末。GMの代理操作でも使用コスト・封印・対象を確認 |
| 記録を見つけられない | 現在のルームの「戦闘記録」を開きます。削除後の復元機能はありません |

## 3. 進行中に介入・復旧する

### 3.1 キャラクターを代理操作・編集する

「📝」の簡易編集には、配置済み・HP1以上で、期限切れの召喚体ではないキャラクターだけが表示されます。GMはPLを含むキャラクターの移動・宣言を代理操作できます。盤面の駒本体をダブルクリックして詳細を開きます。非公開スキル（`hidden_skills`）の閲覧・編集、画像、サイズ、未配置へ戻す等は、GM向けに表示される項目から操作します。

スキルの公開・非公開は、GMが詳細のスキル一覧にある「公開」チェックで切り替えます。「⚙」内ではありません。持ちキャラの成長操作とも別です。キャラクター所有権の譲渡後も移動・削除等の権限マップが同期しない既知不具合は台帳§16に保持し、復旧の標準手順として所有権譲渡を案内しません。

### 3.2 バフ・状態・アイテムを調整する

ドックの「📝」（簡易ステータス編集）で対象キャラクターの「GM Buff / Item Control」を開きます。

1. バフ付与はバフを選び、継続（`lasting`）、待機（`delay`）、必要な場合だけ追加値（`count`）を設定して送信します。`count`の意味はバフごとに確認します。
2. バフ解除は、付与中のバフ一覧から選びます。サーバーへは`buff_id`で送信します。
3. 状態の付与は状態異常とスタックを指定します。亀裂を継続させる場合は「継続R」も指定します。バフの残りラウンドと状態値を混同しないでください。
4. アイテムはIDと増減数を指定します。正の整数は付与、負の整数は減少、0は使えません。所持不足などで拒否された場合は更新されません。
5. 送信後、ログに付与・解除・増減の記録が出たかと、同期後の値を確認します。記録が出なければ失敗しています。サーバーの`gm_buff_error`・`item_adjust_error`を表示するクライアント処理はなく、パネルの「送信: …」は成功通知ではありません。

バフ名だけを送って動的バフを作る操作は使えません。定義と効果は[C01](C01_JSON_Definition_Master.md)、API仕様と検証境界はF01 Part 1を参照してください。

### 3.3 終了・リセットを使い分ける

通常の遭遇終了には2.4の「戦闘終結」を使います。右側の「R終了」はラウンド終了の介入で、遭遇の戦闘記録を確定する操作ではありません。マッチ画面の強制終了も別です。

「リセット」は「戦闘リセット設定」を開き、リセットする項目を選びます。対象キャラクターは選べず、配置済みと未配置で戦闘不能のキャラクターが自動で対象になります。

| 操作 | 実装の処理・注意 |
| --- | --- |
| 上記の内容でステータスのみリセット | HP全快・MP全快・FPリセット・状態異常解除・バフ/特殊状態リセットを選択。ラウンドは0、宣言/スロット等はクリア、召喚体は除去。対象は配置済みまたはHP0以下のキャラで、生存した未配置キャラは状態更新の対象外 |
| ログのみリセット | 現在のルームのログ配列をクリア。戦闘記録や長期保全アーカイブを一括消去する操作ではない |
| 完全リセット（全キャラ削除・初期化） | ルーム内キャラを全削除し、ラウンド等を初期化。持ちキャラ本体の削除とは別 |

バフリセットは追加バフを除去して初期所持分へ戻す処理です。配置だけを未配置へ戻す旧説明のリセット項目はありません。駒を未配置へ戻す場合は詳細の設定から行います。

リセットは通常の資源回復ルールを決める操作ではありません。具体的な使用はGMの判断・シナリオ指定に従います。選択項目の連動、FP・状態の内部フィールド、出身効果の再適用は`manager/battle/common_manager.py::reset_battle_logic`を正として扱い、細部を公開手順として確定する前に4Fで実機確認します。

### 3.4 再入室・進行停止から戻る

表示が古い場合は、再読み込みして同じルームへ再入室します。参加資格が残っていれば参加コードは不要です。再入室は現在の状態と解決表示を再取得するもので、戦闘計算・ラウンド終了をもう一度行う操作ではありません。

進行役が退出した場合は、残ったGMが引き継ぎます。戦闘専用ルームの例外は2.6です。保存・ログ保全の内部仕様はF01 Part 7、退出と同期はPart 13を参照します。

### 困ったとき（介入・復旧）

| 症状 | 確かめること |
| --- | --- |
| バフが反映されない | GMで在室しているか、IDが有効か。ログの付与・解除記録と同期後の値を確認。記録がなければ失敗 |
| バフの名前だけで解除できない | 付与中一覧のIDを持つバフを選びます |
| アイテムの増減が拒否される | 0以外の整数か、減らす数量を所持しているか |
| 再入室しても進行しない | 再入室自体は処理を進めません。進行役と現在の段階を確認 |

## 4. シナリオ用の素材を作る

### 4.1 NPC・エネミーのタグ

キャラ作成ツールで`characterType=scenario`を選ぶと自由タグ欄が表示されます。1件25文字以内で入力して「追加」、不要なタグは削除します。一時的に無効にするタグは「有効」のチェックを外して保存します。

個数上限はありません。改行・26文字以上は拒否されます。GM権限で保存・投入してください。無効タグは赤字・取り消し線で表示され、condition判定とPvE自動対象選択に使われません。PLの出身・輝化由来タグとは分けて扱います。

### 4.2 敵の行動チャート

敵の詳細設定で「行動チャート有効」と「行動チャート編集（フロー）」を使います。現在は視覚的なフロー編集で、内部保存が`behavior_profile`のJSONです。

1. 「初期ループ」（`initial_loop_id`）を選び、ループのステップに使用スキルを登録します。
2. 各スキルの対象候補を上から優先順に並べます。陣営は行動者から見た相手陣営・同陣営・全員・自身です。画面の「敵陣営」は、この相手陣営を指します。必須タグは複数ならANDです。
3. 「＋」でフォールバック候補を追加し、上下で順序を調整します。候補が全部空なら、そのスキル行だけがキャンセルされます。
4. 行動後に必ず移る場合は「スキル使用後にループ遷移」で遷移先を指定します。条件遷移（`transitions`）では、自身のHP割合などを使えます。自身／HP割合（%）／以下／40ならHP40%以下です。
5. 遷移先を選んで保存し、次ラウンドのPvE自動intentに反映されたか確認します。

陣営をまたぐ対象候補では、スキル定義の`target_scope=any`等も合わせます。`self`以外では同じ行動者の別スロットも対象になりません。JSON構造・自動処理はC01・D01、バランス設計は[F02](F02_Battle_Balance_Designer_Skill_Manual.md)、シミュレータは[F03](F03_Battle_Balance_Simulator_CLI.md)を参照します。

### 4.3 プリセットを整理・共有する

戦闘専用パネルの「キャラクタープリセット編集」から「プリセット管理」を開き、キャラクター素材・編成・ステージをコレクションと区分へ整理します。シナリオの複数戦闘は、同じコレクション内で区分IDを分けます。

- ステージやコレクションをルームのブックマークへ登録できます。複製や権限変更は行いません。
- 戦闘準備でステージを選ぶと、参照素材を実行用コピーとして配置します。元素材の編集とは別です。
- ルームowner/gmとして配置できても、素材の所有者・編集者でなければ元データを編集できません。削除と共有権限の変更は素材のownerまたはアプリ管理者だけが行えます。編集者には削除権限がありません。参照される素材や編成は削除できず、共有範囲の不整合があれば投入が拒否されます。
- 通常はフォームで編集し、JSONは入出力に使います。アーカイブは普段の一覧から隠す操作で、「アーカイブ済みも表示」から再表示・解除できます。
- 所有者・編集者・閲覧者は現在ルームに参加中の人の表示名から選びます。共有権限を変更できるのは素材のowner（またはアプリ管理者）だけです。共有は素材ごとの設定なので、参照先も利用できるように個別に設定します。ルーム外の指定が必要な場合だけ「内部ユーザーIDを直接指定（上級者向け）」を使います。表示名を内部ID欄へ入力しません。

アプリ管理者の「全プリセット管理」、所有者不在の素材回収・ユーザー削除・完全バックアップはF01 Part 11で扱います。旧「敵一覧保存」のExport/Importと、次節の移送JSONは別機能です。形式エラーのJSONは保存されないため、修正して再投入します。

### 4.4 コレクションを別環境へ移す

1. キャラクター・編成・ステージを同じコレクションへ分類します。
2. コレクション編集の「移送JSON出力」を押します。同じコレクションの素材と、編成→キャラクター・ステージ→編成の参照先が自動で含まれます。参照先が存在しないか閲覧権限がなければ出力は失敗します。
3. 移動先へログインし、「移送JSON取込」からファイルを選び、「内容を確認」を押します。5MB以下、1回1000件までです。
4. 新規・衝突・参照エラー・取込後の所有者を確認します。同じIDの既定は「除外」で、「別コピー」も選べます。「既存を更新」は既存素材の編集権限がある場合だけ選べます。
5. 「DBへ登録」を押し、登録後の参照・公開範囲を確認します。

ローカルと本番は自動同期されません。通常取込の新規・別コピーは元環境のACLを持ち込まず、取込者が所有者、公開範囲は限定公開になります。「既存を更新」は既存の所有者・編集者・閲覧権限を維持します。必要な相手へ改めて共有してください。管理者による別所有者指定、旧JSONの救済とDBバックアップはF01 Part 12です。

### 4.5 データ定義とビルダー

JSON定義は[C01](C01_JSON_Definition_Master.md)に集約しています。スキルの特記処理、`buff_id`基準のバフ・プラグイン、アイテムキャッシュ、輝化・出身、用語図鑑の列・埋め込み記法を参照してください。利用者向けの図鑑説明は[A04](A04_Glossary_Tutorial.md)です。

既存のJSON定義ビルダーの作例は保持します（今回の生成ボタン操作は実機未確認）。

- `CharaCreator/json_definition_builder.html`のEffectsタブには「震盪スキル雛形を生成」があり、`cost=FP:2,MP:3`、WINで`APPLY_BUFF(target)`（`buff_id=Bu-29`、`lasting=3`、`data.count=2`）、HITで`APPLY_STATE(target)`（破裂3）を入力します。出力は特記処理用`rule_data`です。
- `CONSUME_BUFF_COUNT_FOR_GAIN`／`CONSUME_BUFF_COUNT_FOR_POWER`と、凝魔3消費でMP+5／凝魔最大5消費で最終威力上昇のクイックテンプレがあります。
- `condition.param`では`蓄力_count`、`凝魔_count`、`buff_count:凝魔`を使います。`consume_required`、`gains`、`consume_max`、`value_per_stack`、`apply_to`、`min_consume`は`extra_json`へ入力します。

### 戦闘の区切りの後始末（2026-10-20 D25）

通常ルームの戦闘突入・終結では、荊棘重絡を含む状態異常を0にする。召喚体は突入では残し、終結で取り除く（2026-10-21 D25変更、C1）。戦闘中のバフ・デバフは初期効果へ戻し、期限のない付与を含む付与スキルを除く。通常キャラクターのHP・MP・FP・配置は保持する。B5の後始末のうち召喚体除去を終結だけに限定し、重絡0化とバフ初期化は両方で行う。召喚したラウンドは継続期間に数えない（2026-10-21 D25確定）。

### HP0と戦闘不能（2026-10-21 D08裁定）

HPが0になったキャラクターは戦闘不能になり、戦闘から離脱して、駒は盤面から取り除かれます。戦闘不能になったキャラクターの処理は、シナリオおよびGMの指示に従います。 アプリでは未配置（座標-1/-1）として扱います。
