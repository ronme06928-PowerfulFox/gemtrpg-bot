## 1. 目的

戦闘に関わる「試す・調べる・使う」機能を、マスターデータの管理画面とは別の画面にまとめる（名前は「演習場」、論点1）。

- **マスターデータ（計画60）**：スキル・バフ・用語などを作り、承認して公開する場所。スキルの画面には、そのスキルの素の性能（威力の最小・平均・最大と、条件で変わる威力の一覧）までを出す（E02 Part 15「威力の見込み」、PR60-21）。
- **演習場（この計画）**：スキル同士をかち合わせて勝率を見る、本物の処理で1回ぶつける、敵と行動パターンを扱う、その結果をルームのバトルでも使う。

マスターデータの画面がこれ以上膨らまないように、ここで分ける（2026-11-12 ユーザーの構想）。

## 2. 柱（たたき台）

### 2.1 スキルのかち合わせと勝率

2つのスキル（と、それぞれの使う人の値）を選び、マッチで勝つ・引き分け・負ける確率と、威力の出方を見せる。

- 威力は「固定値＋ダイス」なので、ダイスを何千回も振らなくても、両者の威力の分布を組み合わせれば勝つ確率がそのまま出る。使う人と相手の値（補正・状態）を入れれば、戦闘と同じ `calculate_skill_preview` が条件込みの式を出す（PR60-21 で作る見込みの API と同じ部品）。
- 分布で表せない処理（威力の後で決まる効果、乱数を使う特殊な処理など）がどこまであるかは、実装の前に洗い出す。

### 2.2 ルームのバトルでの有利・不利の表示

2.1 の計算を、実際のルームのバトルで使う。例：宣言パネルで、相手が宣言したスキルに対して、自分の候補のスキルごとに勝率か「有利・不利」を出す。

- 計算は軽い（分布の組み合わせ）ので、宣言のたびに出しても負荷は小さい見込み。

### 2.3 本物の処理で1回ぶつける（旧 計画60 Phase 4b）

下書きや公開中のスキル1つと、相手のキャラ・スキルを選び、本物の処理で1回の対決を解決した結果（ダイス・威力・勝敗・付いた状態・ログ）を見せる。計画60（完了）の構想「試し撃ち」から移した。

- `manager/sim/`（計画30、F03）は動かす間アプリ全体の部品を差し替えるため、本番のプロセスの中では動かさない。**別のプロセス**で動かし、そのプロセスの辞書にだけ下書きを重ねる。Render のメモリが足りるかは、実装の前に測る。
- 短い戦闘を何回も回す集計は、今の CLI（F03）をローカルで使う（マスターデータベース・プロジェクト「段階1の決まり」の試し撃ちを引き継ぐ）。

### 2.4 敵と行動パターン（ユニット管理との関係）

[ユニット管理](../implemented/D01_Play_Mode_Specs.md#part-4-ユニット管理計画61)の敵・行動パターンを参照する（§6 論点4）。敵を相手にした 2.1・2.3（「この敵のこのパターンに対して」）は、置き場にかかわらずここから使えるようにしたい。

## 3. 使える部品

- `calculate_skill_preview`（`manager/game_logic.py`）：使う人・相手の値から、条件込みのダイスの式と幅を出す。
- PR60-21 の威力の見込みの API（E02 Part 15、`manager/catalog/power.py`）：素の性能の計算。2.1 の土台になる。
- `manager/battle/duel_solver.py`・`resolve_match_runtime.py`：マッチの解決。勝敗の決まり（同値のとき・守備・回避・一方攻撃）はここに合わせる。
- `manager/sim/` と CLI（F03）：本物の処理を回す。
- ユニット管理の敵・行動パターン。

## 4. 画面の置き場

メインメニュー（2026-11-16 実装、E02 Part 18）の**上の大きなカード**に「図鑑」の隣で足し、6枚にする（全員が使うので、制作者向けの「データ管理」の小さなボタンには置かない。2026-11-18 ユーザー決定）。開くとメニューの下の全幅の画面（`#drill`）になる。

本体は**練習用のルーム**（論点7）：使う人と相手を選ぶと、保存しない一時的なルームが開く。見た目と操作は本物のルームの画面を簡略化した物で、キャラの配置は固定。宣言するときに5段階が出て（PR63-3 と同じ表示）、マッチは本物の処理で振る。勝率と分布の詳しい図（PR63-2 の画面）は、そこから「詳しく見る」で開く。

## 6. 論点（2026-11-18 決定）

1. **画面の名前**：**演習場**。メインメニューの上の大きなカードに置く（§4、2026-11-18 ユーザー決定で「データ管理」から移した）。
2. **勝率の範囲**：攻撃同士に加えて、防御・回避・一方攻撃・強硬・牽制・マッチ不可の決まりまで今の戦闘（`duel_solver.py`）と同じに扱う。出すのは勝ち・引き分け・負けの確率と、勝ったときの威力（ダメージ）の分布まで。付く状態や威力の後で決まる効果は出さない（それは 4 の段階の「1回ぶつける」で見る）。
3. **ルームでの見せ方**：遊ぶ人も GM も全員に、段階で出す。**非常に有利・有利・拮抗・不利・非常に不利の5段階**（真ん中は「拮抗」、2026-11-18 ユーザー決定）で、勝率（引き分けは半分の勝ちとして数える）の境目は 80%・60%・40%・20%（80%以上は非常に有利、60%以上80%未満は有利、40%より大きく60%未満は拮抗、20%より大きく40%以下は不利、20%以下は非常に不利。上下で対になる）。値は宣言の時点のルームの状態の本当の値で計算する（ルームでは敵の値も見えており、隠す値は無い前提）。
4. **ユニット管理との関係**：敵・行動パターン・編成・ステージはユニット管理の共通資源のまま。演習場では敵ユニットを相手（または使う人）に選び、その値とスキルを使う。**比べるのは1対1だけ**（自分のスキル1つと相手のスキル1つ）で、敵のスキル全部との表や行動パターンの手順ごとの一覧は作らない。
5. **使える人**：**全員**。敵のスキルは図鑑と同じく、その人が出会った物（または「図鑑に最初から載せる」の印の物）だけ選べる。制作者・アプリ管理者は全部選べる。
6. **計算の置き場**：**サーバー**。戦闘と同じ Python の部品（`calculate_skill_preview`・勝敗の決まり）を使い、ずれを出さない。分布の組み合わせは軽いので、宣言のたびに候補ごとに計算してよい。
7. **演習場の本体（2026-11-19 決定）**：**練習用のルーム**。入力の欄と図の画面（PR63-2）を見たユーザーが、「各種コマンドやボタンを簡略化したセッションルーム（キャラの配置も固定）で宣言し、そのときに有利・不利が出る」形を望んだ。本物のルームの画面と処理を使う、保存しない一時的なルームにする（ブラウザだけの見かけのルームは、部品をサーバーなしで動かす手間とずれが大きいので採らない）。PR63-2 の画面は「詳しく見る」として残す。
8. **練習用のルームの作り（2026-11-19 決定）**：
   - **相手の操作**：使う人も相手も自分で宣言する。相手が敵ユニットなら「行動パターンで自動」に切り替えられる。
   - **ラウンド**：ラウンド開始・速度ロールの操作を飛ばし、開くとすぐ宣言できる。マッチが終わったら自動で次のラウンドの宣言へ戻る。
   - **元に戻す**：HP・状態・バフはマッチの後も残り、続けて戦える。「最初に戻す」で選んだときの値に戻す。
   - **寿命**：一人につき1つで、他の人は入れない。メニューへ戻る・接続が切れると、少し待って消す。DB に保存せず、ルームの一覧にも出さない。
   - **残すパネル**：配置を固定したマップ、宣言パネル、マッチ・解決の表示、ログ。左の列は即時行動・アイテム・値の修正（📝、練習でも値を直すのに使う）・矢印・用語・音・演出を残す。
   - **隠す部品**（2026-11-19 試作で確定）：左の列のキャラの追加・待機列・探索への切り替え、右上の戦闘記録・戦闘終結・ラウンドの開始と終了・保存・待機列・リセット・戦闘モード、背景の設定、参加者の一覧、チャットの入力欄と絞り込み。見出しのルーム名は「演習場」。
   - **練習の操作の置き場**（2026-11-19 ユーザー決定、試作の C）：一番上の見出しの帯。宣言窓や敵詳細を開いていても隠れない。中身は「相手：自分で｜自動」の切り替え、「⟲ 最初に戻す」、「詳しく見る」、「キャラを選び直す」。メニューへ戻るのは見出しの 🏠。

9. **PR63-5 の中身（2026-11-20 決定）**：
   - **足せる相手**：使う人と相手の両方。素の値・持ちキャラ・敵ユニットのどれにも足せる。練習用のルームの写しのパレットに足すだけなので、作りは一つで済み、元のデータは変わらない。
   - **選べる範囲と数**：図鑑で読める物だけ（論点5 と同じ。制作者・アプリ管理者は全部）。数の上限は無く、足した物は宣言窓の候補に並ぶ。
   - **図鑑の入口**：付けない。演習場の選ぶ画面から足すだけにする。計画66 の PR66-6 は取り下げ、計画66 を閉じた。
   - **補正**：足したキャラの今の値で計算する（`{物理補正}` などはパレットの決まりどおり）。補正を変えたいときは今あるルームの 📝 で直し、新しい入力欄は作らない。

## PR63-4 の作り（2026-11-19）

第一案のメモリの登録簿を採用する。`manager/practice_rooms.py`に予約名`__practice__:<user_id>`と所有者・初期状態・切断期限を持ち、状態本体はactive_room_statesだけに置く。DBのRoom/RoomMemberを作らない。予約名は通常のルーム作成では使えず、期限切れの予約名を読み込んでも通常ルームとして復活させない。管理者も他人の練習には入れない。1人1件で、再作成時は既存のSocket参加・保存予約・状態・ラウンド用ロックも片付ける。

DBを前提とする境界を調べ、次の箇所で先に予約名を判定する。

- room_accessの役割・所有者・入室membership：登録簿の所有者だけGM。通常の役割判定は従来どおり。
- HTTPのenter_room/load_roomとSocketのjoin_room：所有者を検査し、DBのmembershipやGM PINを使わない。sessionのentered_roomsだけで所有者検査を迂回できない。
- room_manager.get_room_state：メモリだけで取得。save_specific_room_state/flush_room_state_nowとdata_manager.save_room_to_db：保存しない。汚れたルームにも加えず、削除時は残った保存予約を破棄する。
- ロビーはDBのRoomだけから作るので、練習の登録簿を加えない。HTTPのcreate_roomは予約名を拒否し、save_roomは練習の状態の丸ごとの上書きを拒否する。
- ログはメモリの最新500件だけに切り詰め、DBのログアーカイブに送らない。出会いの全入口はencounters.recordを通るので、ここで予約名を除く。
- メニューへの退室・別室への入室は即時に破棄。切断では60秒を猶予とし、再入室で期限を解除する。作成だけして入らなかった場合も60秒で破棄する。単一の掃除ループを使い、ルームが空になれば止める。タブのsessionStorageにはルーム名だけを保ち、再接続時は所有者と期限をサーバーで確認して入り直す。ルームの状態はブラウザーへ保存しない。

作成APIはキャラの値を受けず、選択元とIDだけを受ける。POST /api/drill/characterと共通の変換を使って2人を再構築し、25マス四方のマップの真ん中の列の味方(10,12)・敵(14,12)に配置する。空キャラもサーバーの既定値で作る。戦闘セッションは既存の部品で開始し、既存process_round_startを呼ぶ。通常の開始処理がSocketの文脈を使うため、初回の開始は所有者のSocket入室時に行う。素の値はHP20・MP20と基本の一太刀を既定にする。自分で操作するときはPvP、自動はPvEの既存の計画・自動宣言を使う。切り替えは現在のラウンドの敵の宣言を再構築し、HP等は維持する。

解決表示の完了から既存のラウンド終了を呼ぶ経路を使い、練習だけ続けてprocess_round_startを呼ぶ。HP・状態・ログは維持し、戦闘不能でも自動回復しない。「最初に戻す」は登録簿に保存した開始前の写しに戻して、初回のラウンド開始を行う。

画面は案C：通常の戦闘のDOMと部品を使い、bodyの練習用クラスで不要な操作だけを隠す。見出しに相手の操作・リセット・詳しく見る・選び直すを置く。配置を変える要求はサーバー側でも拒否する。詳しい分布はmountDrillの詳細モードで今の2人の写しと宣言を読み、キャラの選択・値の編集を出さない。閉じるとルームへ戻る。メニューの#drillは2人の選択だけにし、選び直す際は選択元とIDをメモリで戻す。
