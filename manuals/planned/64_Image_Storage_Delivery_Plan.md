# 計画64：画像の保存と配信

作成日: 2026-11-14
状態: 第1段階は完了（6ba1278、本番で表示を確認）。第2段階を実装し、第3段階の調査を記録した。論点3・5は未決定。

## 1. 目的

キャラクター・背景などの画像を、利用者が URL を意識せずに使え、表示が速く、保存と転送の量が膨らまない形にする。Cloudinary の無料枠が溢れそうになったときに、保存先を移せる作りにしておく。

## 2. 今の作り（2026-11-14 調査）

- **アップロード**：`app.py` の `upload_image` が、受け取った画像を Cloudinary の `gemtrpg/characters`・`gemtrpg/backgrounds` に送る。受け取りの検査は `manager/image_upload_validation.py`（10MB まで、PNG・JPEG・GIF・WebP）。送るときの加工は画質の自動（`quality: auto`）だけで、幅の上限は無い（「width制限を撤廃」のコメント）。
- **登録**：`image_registry` の表（`models.py` の `ImageRegistry`）に、名前・URL・`public_id`・種類・公開範囲・アップロードした人を持つ。削除は表と Cloudinary の両方から消す（`delete_image_api`）。
- **選択**：`static/js/image_picker.js` の `openImagePicker`（ギャラリー・新規アップロード・デフォルト素材）。デフォルト素材は `static/images/` から配る（`get_local_images`）。
- **表示**：配るのは預けた画像そのもので、配るときの加工は無い。ギャラリーも元の画像を `background-image` で並べるので、開くと全部を元の大きさで読む。
- **切り抜き**：切り抜いた画像は `canvas.toDataURL('image/png')` の data URL になり、キャラクターの JSON（`image`、元は `imageOriginal`）にそのまま入る。ルームの状態と通信が重くなる。

## 3. 使う量の見積もり（2026-11-14）

Cloudinary の無料プランは月25クレジット。1クレジットは保存1GB・転送1GB・変換1000回のどれか（[公式](https://cloudinary.com/documentation/billing_and_plans)）。

- 5人で1回遊ぶと、キャラの画像8枚と背景2枚を各人が1回ずつ読み（約22MB）、GM がギャラリーを開くと150枚 × 0.4MB で約60MB。合わせて約0.1クレジット。月8回で転送1クレジット弱、保存は300枚 × 0.5MB で0.15クレジットほど。
- 大きく増えるのは、大きな画像をそのまま預けたとき、ギャラリーの画像が増えたとき、ブラウザーのキャッシュが効かないとき。
- 見積もりは仮の数。Cloudinary の管理画面の使用量と比べて直す。

## 4. 構想（たたき台）

### 4.1 端末で整えてから預ける（根本の方針の案）

アップロードの前に、ブラウザーで画像を縮め（キャラは長い辺1024px、背景は1920px など）、WebP にしてから送る。同時に一覧用の小さな版（サムネイル）も作って預ける。

- 配るときの加工に頼らなくなるので、保存先が Cloudinary でも R2 でも自前のディスクでも同じに動く。
- ファイル名を中身のハッシュにすれば、同じ画像は1つにまとまり、ブラウザーと CDN に長く覚えさせられる。
- 切り抜きも、data URL ではなく、切り抜いた画像を同じ流れで預ける。

### 4.2 すぐ効く直し

- ギャラリーをサムネイルで見せる（Cloudinary なら URL に `w_200` などを足すだけでもよい）。
- アップロードで長い辺に上限を付ける。
- 切り抜いた画像を data URL で持たない。

#### 第1段階：同梱素材の転送量とキャッシュ

- 「暗い遺跡洞窟」の原寸 PNG を、Pillow で長辺 1920 px の WebP に置き換える。画質を 2〜3 通り試し、同じ盤面を拡大して暗部・遺跡の輪郭・駒の周辺を見比べ、基準を満たす最小の候補を選ぶ。本番でこの背景を選んでいたルームは、GM が選び直す。
- 変更前は WhiteNoise の既定値 60 秒を過ぎた再訪で背景が `304` になり、本文の再転送はなかった。再検証の往復を減らし、ファイル名にハッシュのない素材の差し替えが古いキャッシュに残る期間を抑えるため、候補のうち最短の 1 日を採用する。
- アプリが生成する同梱画像 URL を `/static/images/…` にそろえる。保存済みのキャラクター・ルーム背景にある `images/…` が引き続き読めるよう `/images/` の配信経路を保つ。Cloudinary の画像と保存先の検討は後の段階で扱う。
- 背景の初回転送を元の半分以下にし、GM が必要とする暗部の形を盤面の拡大時にも見分けられ、再訪と戦闘の進行が遅くならないことを採用基準とする。6 体で 1 ラウンドの解決完了まで、変更前後それぞれでキャッシュを消した初回・直後の再訪・60 秒経過後の再訪を測る。背景と全 HTTP の転送量、入室操作から背景表示とロード画面の終了までの時間、同じ画像の二重読み込みを確認する。

画質 70・80・90 を比較し、盤面 180% で暗部の石の継ぎ目と輪郭を追える最小の画質 80（109,264 B）を採用した。ローカル Chrome の初回転送は背景が 5,957,510 B から 109,568 B、全 HTTP が 7,723,642 B から 1,761,442 B。変更後は 60 秒経過後も背景をディスクキャッシュから読み、出血のアイコンは初回に 1 URL から 1 回だけ転送された。配信仕様は [F01](../implemented/F01_Operations_Manual.md#同梱画像の配信計画64-第1段階) に記載する。

#### 第2段階：預ける前に整える・切り抜きを預ける・同梱のアイコン（2026-11-22 決定）

- アップロードの前に、ブラウザーで長い辺をキャラ 1024 px・背景 1920 px 以内に縮め、WebP にしてから送る。元の画像は預けない。小さい画像は大きくしない。動く GIF は縮めるとコマが失われるため、そのまま送る。
- 切り抜きは data URL をキャラのデータに埋め込まず、512×512 の WebP にして同じ流れで預け、キャラには URL だけを持たせる。切り抜いた画像はギャラリーに並べない。
- 同梱の状態アイコン（`static/images/*.png`、表示は 16〜24 px）を、ファイル名と形式を変えずに長い辺 96 px へ縮める。
- 切り抜きは `image_registry.type = crop` で区別する。キャラ削除時の扱いは §6 の論点5で決める。切り抜きを送れない場合は通知して元画像を使う。
- サムネイルは後の段階で扱う。

第2段階では静止画に画質 80 相当を採用。同梱アイコン7種のファイル合計は 2,794,770 B から 84,013 B に減った。送信と切り抜きの仕様は [F01](../implemented/F01_Operations_Manual.md#画像の送信と切り抜き計画64-第2段階) に記載した。

#### 第3段階：今ある画像を縮め直す（2026-11-22 決定、進め方は調査してから）

- Cloudinary に今ある画像と、キャラのデータに埋め込まれた切り抜きの data URL を、第2段階と同じ大きさ・形式に縮め直す。元に戻せないため、先に元の画像を手元へ控える。
- 画像の URL はキャラ・ルーム・ユニット・登録の表など複数の場所に保存されている。どこにいくつあるか、URL を変えずに置き換えられるか、変わるなら参照をどう直すかを調べてから、手順を決める。実行はユーザーが件数と控えを確かめてから行う。

**保存先の調査（2026-11-22）**

| 保存先 | 棚卸しする項目 |
| --- | --- |
| `image_registry` | `url`、`public_id`、`type`、`visibility`。ここに載らない直貼り URL や旧切り抜きもある。 |
| `owned_characters.data` | `image`、`imageOriginal`。過去に保存した `image` に切り抜きの data URL が入り得る。 |
| `rooms.data` | `characters[*].image`・`imageOriginal`、`exploration.backgroundImage`、`battle_map_data.background_image`、既存の `map_data.backgroundImage`。`active_match` のキャラ写し、戦闘の再開用データ、待機列の入れ子、`stage_avatar_profile.icon` も走査する。稼働中は `active_room_states` が正本。 |
| `catalog_entries.payload`、`catalog_drafts.payload`、`catalog_history.payload` | ユニットの `image`、ステージの `background`（文字列または辞書の `background_image`、`backgroundImage`、`background_url`、`backgroundUrl`、`image_url`、`image`）と `stage_avatar.icon`。敵・味方の編成は原則 `unit_id` で参照する。 |
| 履歴・書き出し | `room_log_archives.payload` と JSON 書き出し（持ちキャラ・ユニット・ログ）は別枠で数える。履歴は資料として保持し、再取り込み対象のファイルは移行時に別途照合する。 |

**置き換えの候補**

| 案 | URL と復旧 |
| --- | --- |
| A. 同じ `public_id` へ上書き | `overwrite` で置換できる。`invalidate` は CDN 側のキャッシュ対策で、ブラウザー等の対策には新しい版付き URL を使う。`secure_url` の版が変わり、PNG/JPEG を WebP にすると拡張子も変わる。旧拡張子は旧形式の配信指定になるため、同じ ID でも参照の更新を前提とする。復旧には旧版の控えが要る。[上書き](https://cloudinary.com/documentation/upload_parameters#replacing_existing_assets)・[URL の形式と版](https://cloudinary.com/documentation/image_transformations#asset_versions) |
| B. 新しい `public_id` で登録し参照を切り替える（推奨） | 旧 URL → 新 URL の対応を保存し、確認済みの現行参照だけを切り替える。旧画像を残したまま表示確認と参照の切り戻しができる。移行中は新旧の保存量が重なる。data URL も同じ対応表で置換できる。 |

どちらもローカルで変換済みのファイルを送れる。Cloudinary は画像1件のアップロードを変換1回に計上し、同じ ID の上書きも含む。新たな配信派生を生成すると別途計上されるため、見積もりでは新 URL から保存形式を直接配る。旧拡張子での配信は派生生成の可能性がある。[変換の数え方](https://cloudinary.com/documentation/transformation_counts#transformation_counting_basics)

**ユーザーが読み取りだけで見積もる手順**

1. [F01 の PostgreSQL 手元バックアップ](../operations/postgres_backup_runbook.md) に従って `pg_dump` と SHA-256 を取得し、別のローカル DB に復元する。DB の控えには URL と data URL は入り、Cloudinary に置いた画像ファイルは別途控える。
2. ローカル DB の対象 JSON を再帰走査し、表・行ID・JSON パスごとに参照数を数える。Cloudinary URL は登録表の `public_id` と照合して同じ資産をまとめる。data URL は base64 を復号し、SHA-256 で重複をまとめて件数・復号前後のバイト数を記録する。履歴・ログ・外部 URL・同梱 URL・未解決の参照は別欄にする。
3. Cloudinary Admin API の一覧取得（`next_cursor` で全ページ）を使い、現在の `asset_id`、`public_id`、種別、版、形式、幅・高さ、`bytes`、`secure_url` を読む。登録表と突き合わせ、参照のみ、登録のみ、Cloudinary のみに分ける。フォルダーの絞り込みは固定フォルダーモードなら `prefix`、動的モードなら asset folder を使う。[Admin API](https://cloudinary.com/documentation/admin_api#get_resources)
4. 候補の現行原本を Media Library の原本ダウンロードで控える。これは Cloudinary が現在保存する版を指す。旧アップロード時の加工前のファイルまで必要なら、持ち主の控えや版履歴を照合する。バックアップ済みの旧版は `download_backup` で取得できる。ID・版・旧 URL・形式・バイト数・SHA-256 を控えの一覧に残す。手元で用途別に変換したバイト数を足し、旧→新の差、移行中に重なる保持量、アップロード予定件数を数える。GIF、形式と寸法が適合済みの画像、変換後に大きくなる候補、同じ画像を複数用途で使う候補は別欄で確認する。[原本ダウンロード](https://cloudinary.com/documentation/dam_editing_and_transformations)・[バックアップ済み旧版](https://cloudinary.com/documentation/backups_and_version_management#downloading_a_version_of_an_asset)

切り替えを実行する段階では、保存待ちのルームを確定してから書き込みを止め、メモリ上の旧状態が DB 更新を上書きしない状態で作業する。第3段階は本番の接続・実件数の取得・置換を行わず、方式の判断を残した。

### 4.3 見張りと片付け

- Cloudinary の使用量を API で取り、アプリ管理者の画面に出す。
- どのキャラ・プリセット・ルーム・背景からも使われていない画像を一覧にし、消せるようにする。

### 4.4 保存先を差し替えられるようにする

保存・削除・URL 作りを1つの部品に集め、保存先を設定で選べるようにする。候補：

| 保存先 | 無料枠 | 加工 | 向き不向き |
|---|---|---|---|
| Cloudinary（今） | 月25クレジット（保存・転送・変換で分け合う） | 配るときに自由に加工 | 今のまま使える。溢れると有料（Plus は月 $89〜99 と資料で食い違う） |
| Cloudflare R2 | 保存10GB、書き込み100万回、読み出し1000万回／月、転送は無料（[公式](https://developers.cloudflare.com/r2/platform/pricing/)） | 無し。Cloudflare の画像変換は無料プランで月5000種類まで（[公式](https://developers.cloudflare.com/images/pricing/)） | 転送が増えても無料。公開には Cloudflare に置いた自分のドメインが要る（`r2.dev` は回数の制限があり本番向けでない） |
| 自前のディスク（VPS・ミニPC） | 機械の容量しだい | 無し（4.1 で不要にする） | 前に Cloudflare の CDN を置けば速い。バックアップは自分で取る |

## 5. 対象範囲

対象とするもの：画像のアップロード・登録・選択・表示・削除、使用量の見張り、保存先の差し替え。

対象としないもの：アプリ本体の置き場（Render からの引っ越し）。考えるときは別に立てる。
