# 49 通常ルーム戦闘突入・戦闘終結管理計画

**作成日**: 2026-09-01
**最終更新**: 2026-09-01
**状態**: 方針確定・未着手
**対象**: 通常ルームの戦闘画面、戦闘セッション状態、Socketイベント、GM操作、戦闘一時状態
**関連仕様**: [B03 Select/Resolve確定仕様](../implemented/B03_SelectResolve_Spec.md) / [D01 プレイモード・ステージ仕様](../implemented/D01_Play_Mode_Specs.md) / [E02 UIコンポーネント仕様](../implemented/E02_UI_Component_Specs.md) / [A02 GM・管理者向け運用マニュアル](../implemented/A02_GM_Creator_Manual.md)

## 1. 目的

通常ルームをTRPGシナリオで使う際に、GMが戦闘画面内で明確な戦闘の区切りを管理できるようにする。

GMは準備・演出・戦闘・戦後処理を同じ戦闘画面で運用する。戦闘の開始操作は **「戦闘突入」**、終了操作は **「戦闘終結」** とし、どちらもUI上の固有の操作名として固定する。

本計画は通常ルームを対象とする。戦闘専用モードの既存「戦闘突入」、および探索パートの `mode: battle / exploration` 切替は対象外とし、挙動を変更しない。

## 2. 背景と現状

通常ルームにはラウンド、タイムライン、Select/Resolve、マッチ、戦闘リセットの機能があるが、シナリオ中の一つの遭遇を表す明示的な状態がない。このため、戦闘の前後をUI・ログ・一時状態のいずれでも一貫して区別できない。

既存の `room_state['mode']` は探索画面と戦闘画面の表示切替のための値である。本機能をそれで実装すると、探索機能との不要な連動、既存UIの切替、副作用の拡大を招く。したがって、戦闘画面内の状態として別に管理する。

また、既存の `BATTLE_START` / `battle_start_effect` はキャラクター追加や戦闘リセットにも使われている。これを「戦闘突入」へそのまま接続すると、FP付与、召喚、伝授スキルなどが同じ遭遇中に重複適用されるおそれがある。

## 3. 決定事項

| 論点 | 決定 |
| --- | --- |
| 管理場所 | 通常ルームの戦闘画面内だけで管理する。探索パートには連動させない。 |
| 状態 | `room_state['combat_phase']` を `ready`（戦闘準備中）または `active`（戦闘中）として保持する。 |
| 操作権限 | 「戦闘突入」「戦闘終結」はGMのみ実行できる。 |
| 開始後のラウンド | 戦闘突入と第1ラウンド開始は別操作にする。GMは突入後に配置や演出を確認してからラウンドを開始できる。 |
| 終結時に保持する状態 | キャラクター、配置、HP、MP、FP、召喚体を保持する。召喚体を残すか削除するかはGMが既存の手動操作で決める。 |
| 終結時に消去する状態 | タイムライン、未解決宣言、resolve queue、active match、ラウンド進行中の一時情報、ラウンド制バフ・デバフ、状態異常スタック、持続・恒久の明示がない一時バフ、伝授スキル、行動済み・戦闘内使用フラグを消去する。 |
| 終結結果 | GMは終結時に `VICTORY`、`DEFEAT`、`RETREAT`、`INTERRUPTED` から結果を選択する。全参加者に結果演出を表示し、戦闘記録へ保存する。 |
| 戦闘記録 | 初版では直近の戦闘1件を保持し、開始・終了情報、結果、ラウンド数、参加キャラクターごとの与ダメージ・被ダメージ累計を表示する。 |
| ダメージ帰属 | 原因キャラクターを特定できるダメージはそのキャラクターへ与ダメージとして記録し、被害キャラクターへ被ダメージとして記録する。原因不明の環境ダメージは被ダメージだけ記録する。 |
| 終結方法 | 初版は、未解決の行動があってもGMの確認後に即時終結する。ラウンドを完走してから終結する選択肢は初版では設けない。 |
| 戦闘開始効果 | 初版では既存 `BATTLE_START` を戦闘突入時に再実行しない。専用フックは将来の別設計とする。 |
| GM手動HP編集 | 戦闘記録のダメージ集計から除外する。ダメージ、回復、訂正を安全に区別できないため。 |
| 用語の書き分け | 通常ルームの本機能は「通常ルーム: 戦闘突入／戦闘終結」、戦闘専用モードの既存導線は「戦闘専用: 戦闘突入」と、画面のモード名を必ず併記する。 |
| 戦闘専用モード | 対象外。既存の編成・戦績・自動遷移を変更しない。 |

## 4. 状態遷移

```text
通常ルームの戦闘画面

戦闘準備中 (ready)
  └─ GM: 「戦闘突入」 ──> 戦闘中 (active)
                                 │
                                 ├─ GM: ラウンド開始・終了を繰り返す
                                 └─ GM: 結果を選び「戦闘終結」 ──> 戦闘準備中 (ready)
```

- `ready` では、キャラクター追加、敵・味方の配置、ステータス確認・編集、背景などの戦闘画面の準備操作を許可する。
- `active` でのみ、ラウンド開始、行動宣言、解決開始、マッチ開始などの戦闘進行操作を許可する。
- `active` で「戦闘突入」を受けた場合、状態を変えずエラーまたは状態同期を返す。
- `ready` で「戦闘終結」を受けた場合、状態を変えずエラーまたは状態同期を返す。
- 終結時に解決演出・未解決マッチ・進行中ラウンドがある場合は、GMに確認を求める。確認後はサーバー側で一時状態を閉じ、古いクライアントから届く操作を無効にする。
- 終結時の結果は `VICTORY`（勝利）、`DEFEAT`（敗北）、`RETREAT`（撤退）、`INTERRUPTED`（中断）のいずれかをGMが選択する。結果未選択では終結を確定できない。

## 5. データ契約と互換性

### 5.1 `room_state` の追加項目

初版では、次の項目を追加する。

```json
{
  "combat_phase": "ready",
  "combat_session": {
    "id": "combat_<uuid>",
    "started_at": "ISO 8601日時",
    "started_by": "GM表示名",
    "ended_at": null,
    "ended_by": null,
    "rounds_completed": 0,
    "outcome": null,
    "participants": {
      "character_id": {
        "damage_dealt": 0,
        "damage_taken": 0
      }
    }
  }
}
```

- `combat_session` は戦闘突入時に新規作成し、戦闘終結後も直近の戦闘履歴として保持する。
- Socketイベントと戦闘状態通知には `combat_phase` と、必要に応じて `combat_session.id` を含める。
- `combat_session.id` は、終結済み遭遇の遅延した宣言・解決要求を識別して拒否するために使う。既存の `battle_state.battle_id` を不用意に変更しない。
- `participants` は戦闘突入時点の参加キャラクターを登録し、戦闘中に参加したキャラクターも初回のダメージ発生時または参加時に追加する。表示名ではなくキャラクターIDをキーにする。
- 与ダメージ・被ダメージは、実際に反映されたHPダメージを集計する。回復、MP/FPコスト、ダメージが0になった軽減結果は含めない。
- GMが直接行うHP編集は、ダメージ・回復・訂正を判別できないため集計しない。

### 5.2 既存保存データ

`combat_phase` を持たない既存通常ルームは、互換性を優先して `active` として読み込む。これにより、更新直後に進行中の既存卓がラウンド操作不能になることを避ける。

新規通常ルームは `ready` で作成する。既存の通常ルームだけを `active` として移行するため、新規卓ではGMが「戦闘突入」を明示し、既存卓では更新直後も従来どおり戦闘を継続できる。

`combat_phase` がない既存ルームは、最初に状態を確保する時点で `combat_phase: active` と、`legacy_migrated: true` を持つ戦闘セッションを遅延作成する。開始時刻・それ以前のダメージは不明なため `started_at: null`、`participants` の集計は移行後に観測した分だけとし、画面では「移行済み戦闘」と表示する。これにより、移行直後の戦闘終結でもセッションIDと結果を一貫して保存できる。

## 6. 実装方針

### Phase 0: 変更先の分割とダメージ集計経路の確立

`manager/battle/common_manager.py` と `events/battle/common_routes.py` はともに1500行上限の直前にあるため、本体機能を追加する前に責務を分割する。

1. `manager/battle/combat_session.py` を新設し、戦闘セッションの開始・終結・旧ルーム移行・一時状態の掃除・セッション状態検証を置く。`common_manager.py` は既存リセット処理との接続だけに留める。
2. `events/battle/combat_session_routes.py` を新設し、`request_combat_enter` と `request_combat_conclude`、GM認可、状態通知を置く。`common_routes.py` は既存イベントと共通ガード呼出しだけに留める。
3. `combat_phase == 'active'` を検証する共通ヘルパーを作り、`common_routes.py` のラウンド・intent・resolve系、`duel_routes.py` のマッチ・宣言系、`wide_routes.py` の広域宣言・解決系へ適用する。通常ルームだけを対象にし、戦闘専用モードの既存進行を拒否しない。
4. ダメージを実際にHPへ反映する経路を棚卸しし、戦闘記録用の `record_combat_damage` を共通フックにする。少なくとも `resolve_effect_runtime._apply_damage`、一方攻撃を含む `resolve_match_runtime`、自動広域処理、反射・継続ダメージの各経路から、実際に減少した値と `damage_context` を渡す。回復、ロールバック、GM手動HP編集は対象外とする。

HPを書き換える全箇所を無条件に単一関数へ置換しない。まずダメージとして扱う経路をテストで列挙・集約し、回復・復元・GM訂正とは責務を分離する。

### Phase 1: 戦闘セッションの中核

1. `manager/battle/` に、開始・終結・状態検証を担当する小さなライフサイクルモジュールを追加する。
2. 戦闘突入時に、新しいセッションIDを生成し、前遭遇のタイムライン、intent、resolve queue、active matchなどを初期化する。
3. 戦闘終結時に、キャラクターの恒久状態を保持したまま、進行中の戦闘一時状態だけを閉じる。
4. メモリ上の `active_room_states` を更新し、状態通知、保存予約、重要な節目での即時フラッシュを既存の保存方針に沿って行う。
5. ラウンド完了時に `combat_session.rounds_completed` を更新する。
6. Phase 0で定義したダメージ記録フックで、攻撃側の `damage_dealt` と被害側の `damage_taken` を同じ値だけ更新する。範囲攻撃、反射、継続ダメージ、召喚体によるダメージでも、原因キャラクターを特定できる場合はそのキャラクターへ与ダメージを帰属させる。

既存の `reset_battle_logic` はHP・MP・バフ・キャラクターまで扱うため、通常の戦闘終結には流用しない。共有できる一時状態の掃除だけを抽出し、終結とリセットの責務を分離する。

### 6.1 戦闘終結時の掃除契約

| 区分 | 終結時の扱い |
| --- | --- |
| HP / MP / FP | 保持 |
| キャラクターと盤面配置 | 保持 |
| 召喚体 | 保持。GMが既存の手動操作で削除または継続を選ぶ |
| `lasting` を持つラウンド制バフ・デバフ | 消去 |
| 状態異常スタックと持続・恒久の明示がない一時バフ | 消去。ただし初期データ由来・保持対象として明示された恒久バフは保持 |
| 伝授スキル | 消去 |
| `used_skills_this_round`、即時スキル使用、アイテム使用、戦闘内一回限り使用フラグ | 初期化 |
| タイムライン、slot、intent、resolve queue、active match | 消去 |
| 戦闘結果・ダメージ集計 | 直近の `combat_session` として保存・表示 |

状態異常スタック（出血、亀裂、破裂、戦慄、荊棘など）と、持続・恒久の明示がない一時バフは消去する。一方、キャラクター初期データに由来する恒久バフ、および保持対象として明示されたバフは残す。恒久バフの復元元には既存の `char['initial_state']['special_buffs']` を用い、実装時は既存データを分類して恒久バフを誤って削除しないテストを固定する。

ダメージの帰属は、スキル使用者、反射を発生させたキャラクター、召喚体など、原因キャラクターを確定できる場合にその原因キャラクターへ与ダメージを加算する。自傷は同じキャラクターの与ダメージと被ダメージへ加算する。環境・フィールドなど原因キャラクターを確定できないダメージは、被害キャラクターの被ダメージだけに加算する。

### Phase 2: Socketイベントと認可

1. `request_combat_enter` と `request_combat_conclude` を追加する。終結イベントは結果を必須入力として受け取る。
2. 両イベントで、ルーム所属、GM権限、通常ルームであること、現在フェーズ、任意の期待セッションIDを検証する。
3. 失敗時は、状態を部分更新せず、既存のエラー通知方針に沿って理由を返す。
4. 成功時は、ルーム全員へ状態更新とシステムログを送る。ログには操作名、GM名、戦闘セッションID、結果、ラウンド数を記録する。
5. `common_routes.py`、`duel_routes.py`、`wide_routes.py` の既存ラウンド開始・終了、行動宣言、解決、マッチ関連イベントへ `combat_phase == 'active'` のサーバー側ガードを追加する。

クライアントでボタンを隠すだけではなく、全ての戦闘進行イベントをサーバー側で検証する。これにより、古い画面、再接続、Socketの直接送信でも準備中に戦闘が進まないことを保証する。

### Phase 3: 戦闘画面UI

1. 通常ルームの戦闘画面に、現在フェーズを示すバッジを置く。
2. GMだけに次の操作を表示する。

   | フェーズ | 主操作 | 補助表示 |
   | --- | --- | --- |
   | 戦闘準備中 | **戦闘突入** | 戦闘操作は開始後に利用可能である旨 |
   | 戦闘中 | **戦闘終結** | 開始GM、開始時刻、経過ラウンド数 |

3. 戦闘終結のダイアログでは、`VICTORY`、`DEFEAT`、`RETREAT`、`INTERRUPTED` を必須選択にする。未解決のラウンド・宣言・マッチがある場合は、破棄される一時状態も明示する。
4. プレイヤーにはフェーズ表示だけを同期し、GM操作は表示しない。
5. `play_mode == 'battle_only'` の画面・モーダルは従来の導線を維持し、このUIを表示しない。
6. 終結確定後、全参加者に選択結果を大きく表示する演出ポップアップを送る。表示名は `VICTORY`、`DEFEAT`、`RETREAT`、`INTERRUPTED` とし、ログ・戦闘記録にも同じ結果を残す。
7. 戦闘画面に直近の戦闘記録を表示する。少なくとも結果、開始・終了時刻、ラウンド数、参加キャラクター別の与ダメージ・被ダメージを確認できるようにする。

### Phase 4: 将来拡張（本計画の初版対象外）

- 戦闘突入専用のスキルフック（例: `COMBAT_ENTER`）と、戦闘終結専用のクリーンアップフック（例: `COMBAT_EXIT`）
- 戦闘結果（勝利・敗北・撤退・中断）とGMメモの保存
- 戦闘ごとのログ抽出、戦績・経験値反映との連携

これらを追加する場合は、キャラクター追加時にも実行される既存 `BATTLE_START` と意味・発火回数・永続化範囲を明確に分離する。

## 8. テスト計画

### 8.1 状態遷移

- `ready` のGMが戦闘突入すると `active` になり、新しいセッションIDが作られる。
- `active` のGMが戦闘終結すると `ready` になり、キャラクター・HP・MP・配置が維持される。
- 新規通常ルームは `ready` で作成され、既存保存データに `combat_phase` がない場合は `active` として移行される。
- 既存ルームを移行した戦闘は、`combat_session` が欠落せず、終了時に「移行済み戦闘」として結果を保存できる。
- `active` での戦闘突入、`ready` での戦闘終結は状態を変更しない。
- 同じ要求の短時間連打、再接続後の再送、古いセッションID付き要求でも状態が壊れない。

### 8.2 認可とガード

- 非GM、ルーム外SID、戦闘専用モードからの要求を拒否する。
- 準備中はラウンド開始、宣言、解決、マッチ開始を拒否する。
- 通常マッチ、通常宣言、広域宣言、広域解決の各Socketイベントが準備中に拒否される。
- 戦闘中は既存のGM・所有者権限を維持する。
- 終結後に届いた前セッションの宣言・解決要求を拒否する。

### 8.3 終結処理

- ラウンド未開始、select中、resolve中、マッチ中の各状態から、安全に終結できる。
- 終結後にタイムライン、intent、resolve queue、active matchが残らない。
- HP、MP、FP、配置、召喚体は保持される。
- ラウンド制バフ・デバフ、伝授スキル、行動済み・戦闘内使用フラグは初期化される。
- 状態異常スタックと持続・恒久の明示がない一時バフは初期化され、キャラクター初期データ由来の恒久バフは保持される。
- `VICTORY`、`DEFEAT`、`RETREAT`、`INTERRUPTED` の各結果が保存・ログ・演出表示で一致する。
- 単体・範囲・反射・継続・召喚体・自傷ダメージについて、原因キャラクターの与ダメージと被害キャラクターの被ダメージが一致する。
- 原因不明の環境ダメージは、被害キャラクターの被ダメージだけに加算される。
- GM手動HP編集、回復、ロールバックはダメージ記録へ加算されない。

### 8.4 回帰・品質

- 既存の通常ルームが `combat_phase` 未設定でも従来どおり戦闘操作できる。
- 戦闘専用モードの自動ラウンド進行、既存の戦闘突入、探索モード切替が変わらない。
- 対象Pythonテスト、JavaScript構文検査、`npm run build`、文字コード・文字化け検査、必要に応じて全件 `pytest -q` を実行する。

- [ ] 終結後に前戦闘の未解決宣言、マッチ、タイムライン、resolve queue、ラウンド制バフ・デバフ、伝授スキル、戦闘内使用フラグが残らない。
- [ ] 終結後に状態異常スタックと持続・恒久の明示がない一時バフが残らず、初期データ由来の恒久バフは保持される。
- [ ] GMは終結時に `VICTORY`、`DEFEAT`、`RETREAT`、`INTERRUPTED` を選択でき、全参加者に対応する演出ポップアップが表示される。
- [ ] 直近の戦闘結果、ラウンド数、各キャラクターの与ダメージ・被ダメージが戦闘画面で確認できる。
- [ ] `BATTLE_START` が戦闘突入のたびに重複実行されない。
- [ ] 既存通常ルーム、戦闘専用モード、探索モードの回帰テストを通る。
