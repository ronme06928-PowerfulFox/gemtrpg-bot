# 計画61：ユニット管理（敵・NPC・行動パターン・編成・ステージを、ゲーム全体で共通の資源にする）

作成日: 2026-11-04
状態: **見直し済み（2026-11-14）**。当初の「全プリセット管理のキャラの欄をフォームにする」計画を、「ゲーム全体で1つの共通の資源として、敵・NPC・行動パターン・編成・ステージを管理する『ユニット管理』を作り、今のプリセット管理を置き換える」計画に改めた（§7 論点13〜16）。未決定事項を決め、PR 分割を書き直した（§5）。PR61-2 の画面の試作を作った（§3.8）。PR61-1・PR61-2 を実装済み。[マスターデータベース・プロジェクト](../projects/master_database/README.md)の段階2。

## 1. 目的

敵キャラ・NPC（ステータス・所持スキル・パッシブ）、その行動パターン、編成、ステージを、マスターデータ（計画60）と同じく**ゲーム全体で1つの共通の資源**として作り・直し・使い回せるようにする。

- メインメニュー（計画62の候補。それまではロビー）から開く「ユニット管理」の画面で管理する。ルームの GM は、ルームの中からも同じ画面を開き、そこから敵・編成・ステージをルームに配置できる。
- 1体の敵に、シナリオや場所によって違う行動パターンを複数持たせ、どの戦闘でどのパターンを使うかを選べるようにする。敵のステータスやスキルを直したら、その敵の全部のパターンと、使っている全部の編成に効くようにする。
- 今の「プリセット管理」（人ごとの資産・公開範囲・移送JSON）は、ユニット管理で置き換える。

## 2. 今の作り（2026-11-04 調査）

- **敵キャラ**：戦闘専用プリセットのキャラクター（`resource_type` がキャラクターの `preset_resources` の行）。中身はキャラクターの JSON で、スキルはチャットパレットの `【ID 名前】`、特殊パッシブは `SPassive` の ID 配列で持つ。所有者・ACL・`revision`・コレクションと区分・参照の整合の検査がある（D01 Part 4・6）。
- **行動パターン**：キャラクターの JSON の `flags.behavior_profile` に、1キャラにつき1つ埋め込む（D01 Part 1 §6）。ループ・ステップ・遷移の条件を持つ。編集は `static/js/modals/behavior_flow_editor_modal.js`。
- **編成ごとの差し替え**：敵編成の各メンバーは `behavior_profile_override` を持てる。中身は行動パターンの丸ごとの写しで、配置のときにキャラの `flags.behavior_profile` を上書きする（`manager/preset_deployment.py`、`manager/room_preset_apply.py`、`manager/battle_only_runtime.py`）。編成の画面（`battle_only_enemy_formation_modal.js`）で JSON または行動チャートのエディターで編集する。
- **困りごと**：
  - 同じ行動パターンを複数の編成で使うと、写しが編成ごとに増え、直すときは全部を直す必要がある。
  - パターンに名前が無く、「坑道用」「ボス戦用」のように選んだり探したりできない。
  - キャラ本体のパターンと、編成ごとの写しの、どちらが使われるかが画面から分かりにくい。
  - 敵が使うスキル・パッシブの ID は文字列で書くだけで、マスターデータとのつながり（存在するか、廃止されていないか、どの敵が使っているか）を引けない。

### 2.1 追加の調査（2026-11-14、計画60の完了後）

- **画面**：「プリセット管理」（`battle_only_workspace_modal.js`）が、キャラ・編成・ステージ・コレクションをまとめて扱う。キャラの中身は `battle_only_catalog_modal.js` の生の JSON の欄だけで直す。行動チャートは別のモーダル（`behavior_flow_editor_modal.js`）で、`modals.js` にも古い同じ物が残っている（バンドルの順で後者が勝つ）。

- **写しのパターンを当てる所**：`manager/battle_only_runtime.py`・`manager/room_preset_apply.py`（同名の関数が2つ）・`manager/preset_deployment.py`（正規化しないで代入する）・`manager/sim/preset_loader.py`（F03 の CLI）。持ち回すのは `events/battle_only/catalog_state.py` の3か所と、フロントの3つのモーダル（編成・カタログ・下書き）。キャラの組み立ても `room_preset_apply.py` と `battle_only_runtime.py` に重なっている。

## 3. 構想

### 3.1 ユニット管理（2026-11-14 見直し）

- **共通の資源**：キャラクター（敵・NPC・味方 NPC）・編成（敵・味方）・ステージをゲーム全体で1つずつ持つ。人ごとの持ち主・公開範囲（ACL）は持たない（論点13・15）。コレクション（シナリオごとのまとまり）は、マスターの中の分類として残す。
- **編集の流れ**：制作者（アカウントの「制作者」の印。アプリ管理者は制作者として扱う）が直接保存する。下書き・承認は無い。履歴は残し、前の版に戻せる（論点14・18）。
- **見える範囲**：データごとに「公開」か「制作者・GM のみ」を選ぶ（論点15）。「制作者・GM のみ」は、制作者と、ルームの中から開いたそのルームの GM が見られる。ルームの GM（制作者でない人）は見て配置できるが、直せない（論点19）。制作中の物を隠し、出来た物を公開する、を柔軟に行う。プレイヤー向けの図鑑は別に作る（§6）。
- **画面**：マスターデータとは別の画面「ユニット管理」。一覧・編集・履歴・使用中の一覧などは、マスターデータ（`static/js/master_data/`）の部品を使う（論点16）。ルームの GM が開いたときは「ルームへ配置」ができる。
- **土台**：計画60の `catalog_entries`・`catalog_history` に、新しい種類として乗せる。`preset_resources` は置き換える（§5.2）。

### 3.2 行動パターンをキャラの中の一覧にする

行動パターンを、キャラ1体に1つ埋め込む今の形をやめ、キャラの中に**名前付きの一覧**として持つ（論点12）。

- 名前・説明・中身（今の `behavior_profile` と同じ形）を持つ。パターンの ID はキャラの中で一意。
- パターンは1体の敵に属する。その敵を消すと、パターンも一緒に消える（論点1）。
- 別の敵へ複製できる。複製するとき、ステップのスキルが複製先の敵に無ければ、その場で一覧にして直させる。複製したパターンは別物で、片方を直してももう片方は変わらない。
- 1体の敵が、パターンをいくつでも持てる。パターンが1つ以上あれば、既定は必ず1つ。最初に作ったパターンが自動で既定になり、既定を消すときは別のパターンを既定にしてから消す。パターンが0個の敵は、今と同じ自動の選び方（AI 提案・使えるスキルからのランダム）で動く（論点2）。
- 版はキャラと同じ（パターンだけの版は持たない）。

### 3.3 編成の枠でパターンを選ぶ

敵編成の各メンバーは、行動パターンの写しではなく、**パターンの ID**（同じメンバーのキャラの中の ID）を持つ。指定が無ければ、その敵の既定のパターンを使う。

- 写しの `behavior_profile_override` と、キャラ本体の `flags.behavior_profile` はやめる（後方互換は持たない）。
- 編成の中だけでパターンを変える写しは持たない。少し変えたいときは、編成の画面の「複製して編集」で、同じ敵の別のパターンとして保存する（論点3）。

### 3.4 敵のスキル・パッシブをマスターデータの参照にする

- 保存の前に、存在しない ID・廃止された ID を検査する。
- 「このスキルを使っている敵」「この敵が使っているスキル」を引けるようにする（プロジェクトの共通の土台）。
- 行動パターンのステップが指すスキルも、その敵が持っているスキルかを検査する。

### 3.5 キャラを項目に分けて持つ

- 対象は、ユニット管理のキャラのすべて（敵・NPC・味方 NPC。論点8）。持ちキャラ（F01 Part 9）は対象外。
- 項目：ステータス（最大HP・最大MP・初期HP・初期MP）、パラメータ、スキルの一覧（ID と固有名称・非公開）、その他のパレット行、パッシブ、輝化スキル、アイテム、画像、シナリオキャラクター、GM限定表示、タグ、行動設定（対象の自動選択・スキルの自動選択・予定スキルの公開・行動スロット・スキルの制約）、行動パターン。配置の時に読まれていないキーは持たず、取り込みで捨てる（論点9）。
- チャットパレット（`commands`）は保存しない。配置のときに、マスターの `チャットパレット` 列から作る。マスターでスキルを直すと、全部の敵に効く。ココフォリアへの書き出しは作らない。
- 入口は「JSONインポート」（貼り付け・ファイル読込）。今あるプリセットは、起動時に同じ読み取りで新しい形へ直す（論点11）。

保存の形の例（項目の名前は PR の詳細で確定する）：

```json
{
  "name": "マンティス・ヨールド", "image": "https://res.cloudinary.com/...",
  "scenario": true, "gm_only": false,
  "hp": 253, "mp": 10, "initial_hp": 253, "initial_mp": 10,
  "params": [{"label": "筋力", "value": 12}],
  "skills": [{"id": "E-23", "name": "何がなんでも", "hidden": false}],
  "other_lines": ["1d100 【幸運の判定】"],
  "passives": ["Pa-04"], "radiance": ["S-00"], "items": [{"id": "I-00", "count": 1}],
  "tags": [], "disabled_tags": [],
  "behavior": {"auto_target": false, "auto_skill": false, "show_planned": false, "slot_mode": "normal", "constraints": []},
  "patterns": [{"id": "BP-1", "name": "通常", "note": "", "profile": {"enabled": true, "initial_loop_id": "loop_1", "loops": {}}}],
  "default_pattern_id": "BP-1"
}
```

### 3.6 配置のときの組み立て

新しい形から、ルームで動くキャラ（今の形）を作る関数を1つにし、通常ルームの配置・戦闘専用モード・シミュレーター（F03）が使う。重なっていた組み立てとパターンの当て方（4か所）は消す。

- `commands` は、`skills` の順にマスターの `チャットパレット` から作り（固有名称があれば `【ID 固有名称】` に置き換える）、`other_lines` を後ろに足す。
- 敵として置くときは、編成の枠のパターン ID、無ければ既定のパターンを `flags.behavior_profile` に入れる。パターンが無ければ入れない。味方として置くときは入れない。

### 3.7 試作（2026-11-14）

`node scripts/preset_preview/plan61/build.mjs` で `/_local/preset_preview/plan61/index.html` を作る。データは `data/cache/` のキャッシュ。試作は「プリセット管理」の中に置く前提で作ったが、キャラの編集フォームはユニット管理でもそのまま使える。

- **キャラの画面**：節は 基本情報・ステータス・パラメータ・スキル・パッシブ・輝化スキル・アイテム・行動設定・行動パターン。右に「チャットパレット（配置時）」「保存前チェック」「使用中の編成」。
- **見比べの結果（ユーザー決定）**：レイアウトは「目次＋1セクション」（管理画面と同じ）、スキルは「カード形式」（コスト・効果つき）。
- **JSONインポート**：一覧の上の「＋ 新規作成」から「空のキャラクター」「JSONインポート」を選ぶ。貼り付けとファイル読込、解析結果の表を見てから作る。
- **編成**：メンバーごとにパターンを選ぶ（既定／名前）。「複製して編集」は、同じキャラの別のパターンを作ってその枠で選ぶ。
- **ユーザーの指摘**：
  - キャラ区分は「味方キャラクター」「敵キャラクター」のチェックボックス。
  - 画面の文言は、和語の言い回しを減らし、熟語・カタカナ語で短く書く。
  - 画像は URL の入力欄にせず、ルームの画像選択モーダル（`openImagePicker`）を「画像を選択」から開く。
  - プルダウン（`select`・`datalist`）の候補が左上から開いた。本番では Chrome で確かめ、ずれるときはページの中に候補の一覧を出す。

### 3.8 ユニット管理の画面の試作（2026-11-14、2回目）

同じ `node scripts/preset_preview/plan61/build.mjs` で、試作をユニット管理の画面に作り替えた。データはキャッシュのプリセットを、起動時の移行の結果のつもりで ID を振り直して使う（`U-001`・`F-001`・`ST-001`）。

- **全体**：見出しの「ユニット管理」、タブは「ユニット・編成・ステージ」（件数つき）。左に「＋ 新規作成」・検索・分類・「廃止済みも表示」・一覧（味方・敵・非公開・廃止の札）。見出しに「書き出し・取り込み」。
- **編集**：目次＋1セクション、右に「確認」（保存前チェック・使用中）。下の帯に「廃止／廃止を取り消す」「削除（使用中は押せない）」「版 n・保存」。各種類に「履歴」（版の一覧と「この版に戻す」）。基本情報に「分類」と「公開範囲（公開／制作者・GMのみ）」。
- **編成**：基本情報（編成名・種類・推奨人数）とメンバー（ユニット・数・行動パターン・複製して編集）。確認にメンバーの一覧。
- **ステージ**：基本情報（名前・コンセプト・説明・タグ）、編成（敵編成・味方編成・必要人数）、フィールド効果（種類・対象・値・表示名・説明）、ステージアバター。確認にステージの見え方の見本。
- **書き出し・取り込み**：分類か全件を選んで書き出す（範囲外の参照先は一緒に書き出す）。取り込みは、新規・上書き（版が進む）・参照の確認を表で見てから行う。
- **閲覧者の切替**：制作者（ロビーから）・ルームの GM（制作者でない、ルームから。閲覧のみで「ルームへ配置」）・一般（ロビーから。非公開は一覧に出ない）。
- **試作で見つけた点**：公開の編成やステージに非公開のユニットが入ると、一般の人にも、その編成・ステージの中身から名前やステータスが見えてしまう。保存前チェックの注意（保存は止めない）にする（論点23）。

### 3.9 画面の作り直し（2026-11-15、PR61-2b）

- **今後の配色・装飾**：台帳の情報密度を維持し、一覧の選択行・編集の見出し・確認欄を淡い面色と罫線で区別する。陣営・公開範囲・警告には既存の札と文言を併用し、色だけに依存しない。1280px・680pxで文字のコントラストと読みやすさを確認してから適用する。

PR61-2 の画面はマスターデータの部品の大きさのままで、間延びしていた。Codex にデザインの案を2つ（台帳・シート）出してもらい（`node scripts/unit_ui_proposals/build.mjs` → `/_local/unit_ui_proposals/index.html`）、次に決めた（論点24〜26）。

- **台帳の形**：左は行で詰めた一覧（ID・名前・札）、中央は選んでいる節だけを編集、右は確認。候補の窓も台帳の形で、行ごとにコスト・効果・特記・パレットを見比べる。
- **大きさと空白**：文字は13px ほど。余白は小さく（すき間は4〜8px、枠の内側は8〜10px）。入力欄は中身に合った幅にする（数値は数文字分、名前は1行分。画面いっぱいに伸ばさない）。スキルは1件を1〜2行の行で見せ、長い効果の文は1行で切って、開いたときだけ全文を出す。
- **候補のタブ**：スキルの候補は、マスターデータのスキルの画面と同じ10の分類（Ps・Pb・Pp・Ms・Mb・Mp・B・C・D・E）のタブで分け、検索と組み合わせる。
- **初期状態はなくす**：ユニットは状態（FP・出血など）の初期値を持たない。戦闘の始めから何かを持たせたいときは、戦闘開始時に効果を出すパッシブで表す。蓄力・凝魔は状態ではなく蓄積するバフで、これも同じくパッシブで表す。

### 3.10 ボタンの棚卸しと置き場の決まり（2026-11-15、案）

ボタンを作りながら足してきたので、置き場と言い方が揃っていない。色付けの前に、置き場の決まりを決める。棚卸しは `static/js/units/`（コミット 468d0e1）から拾った。

| 1行 | 行の中・行の右 | 名称変更、このスキルを外す、外す（メンバー）、削除（効果ルール）、条件を解除、タグの × | ふつう・危険 | 「外す」「削除」「解除」「×」が混ざる。タグだけ × |
| 窓 | 窓の見出しの右 | 閉じる | ふつう | — |
| 窓 | 窓の中 | 追加（候補の行ごと）、分類のタブ、解析、新規作成・選択中のユニットを上書き、JSONを書き出す、取り込みを確定・再確認、適用・マスターの名称に戻す、未分類 | 主・ふつう | 主の操作の置き場が窓ごとに違う。候補の「追加」が全部塗りつぶしで、主が並びすぎる |
| 履歴 | 履歴の行 | この版に戻す | ふつう | — |

#### 置き場の決まり（案）

1. **画面全体の操作**は見出しの右。書き出し・取り込み、再読み込み（今の「更新」）、閉じる。
2. **一覧の操作**は一覧の見出しの右に「＋ 新規」を1つ。検索と絞り込みはその下の1段にまとめる。
3. **開いている1件の操作**は下の帯。右に「保存」（主）と「変更を破棄」、左に「その他 ▾」を置き、廃止・削除はその中にしまう（ふだん目に入らず、押し間違えない）。
4. **節の操作**は節の見出しの右。「＋ 追加」は行が何件あっても同じ場所に出る。
5. **1行の操作**は行の右端に、文字で置く。ふつうの操作（名称変更など）を先に、外す・削除は一番右に離す。
6. **窓**は見出しの右に「閉じる」、主の操作は窓の下の右に1つ。候補の行の「追加」は枠だけのボタンにし、塗りつぶしは使わない。
7. **言葉**：一覧から取り除くのは「外す」、データそのものを消すのは「削除」、選んでいる物を空にするのは「解除」。タグの札だけは、札の中の × を残す（札の形で完結し、意味が取り違えにくいため）。
8. **大事さ**：主の操作（塗りつぶし）は1つの面に1つまで。ふつうは枠だけ、危険は赤い文字。色付け（§3.9）はこの3段に合わせる。

#### Codex の照合と足した点（2026-11-15）

Codex が 468d0e12 と照合し、Chrome で確かめた。置き場はおおむね上の案でよく、次を足す。

- **未保存**：「変更を破棄」は未保存のときだけ押せる。下の帯に「未保存」を出す。保存済みの物は保存した内容に戻して同じ節に留まり、新規作成中なら一覧へ戻る。「更新」は「再読み込み」に改める（一覧と開いている1件を読み直す）。
- **確認窓**：共通の確認窓（`static/js/main.js` の `openAppDialog`、49か所で使う）は、今は確定のボタンに最初の印が付き、Enter がどこに印があっても確定を実行する。Enter は印の付いたボタンだけを動かす形をアプリ全体の決まりにし、最初の印の置き場は確認窓ごとに選べるようにする（削除・破棄など危険な確認は「キャンセル側」）。
- **候補の窓**：スキル・パッシブ・輝化スキル・アイテム・メンバーは、追加しても窓を閉じず、検索・分類・一覧の位置を保って続けて選べる。追加した物は候補から消さず「追加済み」と示す（行が詰まって位置がずれないように）。メンバーだけは同じユニットを何度でも追加でき、追加した回数を示す。分類と編成は、行の「選択」で反映して閉じる。
- **書き出し・取り込み**：窓の中を「書き出し」「取り込み」のタブに分け、それぞれの主の操作を1つにする。
- **節**：長い節は「＋ スキルを追加」のように対象名の付いたボタンを見出しの右に置き、見出しごと上に留める。パッシブ・輝化スキル・アイテムは小見出しごとに置く。
- **一覧**：検索と絞り込みは、680px で窮屈なら2段でよい。一覧の先頭が見える高さを比べる。
- **その他**：廃止・廃止を取り消すはふつうの色、削除は区切りの下の赤い文字。削除できないときは理由（「編成で使用中」など）をその場に出す。
- **確認欄**：幅の切り替えは確認欄の見出しに残し、「確認欄を広げる／元の幅に戻す」と書く。680px では「確認へ」の導線を先にする。

## 5. 決めたことと PR 分割（2026-11-14）

### 5.1 決めたこと（論点18〜22）

- **直せる人**：アカウントの「制作者」の印（アプリ管理者は制作者として扱う）。ルームの GM は、ルームの中から開いたとき、そのルームで「制作者・GM のみ」のユニットも見て配置できるが、直せない。
- **環境の間の移し**：ユニット管理の画面で、分類（シナリオ）ごとか全件を JSON に書き出し、もう片方で取り込む。今の移送JSON の後継。`--pull` には含めない。
- **消すと廃止**：使用中の物は「廃止」の印にし、一覧から隠す（使っている所は動き続ける。廃止は取り消せる）。どこからも使われていない物だけ削除できる。
- **ルームへの配置**：ルームの中からユニット管理を開き、ユニット・編成・ステージを選んで「ルームへ配置」する。通常ルームの「プリセット配置」と、戦闘専用モードの編成・下書きの画面は、この入口へまとめる。

### 5.2 Claude が決めたこと

- **土台の表**：計画60の `catalog_entries`（種類＋ID＋中身＋版＋廃止）と `catalog_history`（各版の写し）に、種類として足す。種類は `unit`（キャラ）・`formation`（敵・味方の編成）・`stage`・`unit_collection`（分類）。下書きの表（`catalog_drafts`）は使わず、制作者の保存が直接 `catalog_entries` を書き換え、`catalog_history` に版を残す。見える範囲は `catalog_entries` に列を足して持つ（マスターデータの種類は常に公開）。`preset_resources`・ACL の表はやめる。
- **同時に直したとき**：保存は元にした版を添え、版が変わっていたら止めて、読み直しを促す。
- **保存前チェック**：存在しない ID・廃止された ID・持っていないスキルを指すステップ・既定のパターンの決まりは保存を止める。チャットパレットの食い違いのような注意は止めない。

## 8. 受け入れ条件（暫定）

- [ ] ユニット管理をロビー（のちにメインメニュー）とルームの中から開け、制作者が敵・NPC・編成・ステージを直接作って直せる。履歴から前の版に戻せる。
- [ ] データごとに「公開」「制作者・GM のみ」を選べる。
- [ ] 1体の敵に名前付きの行動パターンを複数持たせ、1つを既定にできる。
- [ ] 敵編成のメンバーごとにパターンを選べ、指定が無ければ既定のパターンで動く。パターンを直すと、そのパターンを使う全部の編成に効く。
- [ ] キャラは項目で持ち、マスターでスキルを直すと配置したキャラのチャットパレットに効く。
- [ ] 存在しないスキル・パッシブの ID と、敵が持っていないスキルを指すステップは、保存の前に検査ではじかれる。
- [ ] CharaCreator の出力を「JSONインポート」で入れられ、今あるプリセット（計画38の敵5体を含む）は起動時に新しい形へ直る。
- [ ] ルームの GM が、ユニット管理から敵・編成・ステージをルームへ配置できる。

- 計画60 Phase 6では召喚テンプレートはJSON編集だけとする。項目ごとのフォームは本計画の敵キャラのフォームと合わせて検討する。
