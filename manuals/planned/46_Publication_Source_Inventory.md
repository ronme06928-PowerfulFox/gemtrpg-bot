## 1. 確認範囲と読み方

対象は初期2冊の全章。重点確認はキャラ作成・戦闘・入室から最初のラウンドまで。基準HEADは `7f53f3178d10bb4f3b7eb9dca8ab2b730e652609` と、計画46関連の未コミット文書変更を含む作業ツリー。世界観のDiscord投稿、公開中のマスターデータ、稼働アプリの実機表示は今回未確認。既存PDFの再生成や本文修正は行っていない。

「出典あり」は執筆材料の所在確認であり、すべてが現行仕様と一致する意味ではない。重点箇所は文書の本文とコードを静的照合した。テストは所在・一部内容の確認のみで、実行していない。一般公開可否は章の掲載方針であり、個別設定の公開許可を確認したものではない。

- **編集可**：材料を確認済み。要約・図解の試作へ進める（公開前検証は別途必要）。
- **要照合**：材料はあるが数値・例外・操作を追加照合する。
- **相違あり**：文書同士または実装と異なる記述を確認。差異台帳で判断する。
- **未確認**：出典内容または公開範囲の確認が必要。

不足は「説明素材」「仕様の判断」「実機確認」「外部資料」に分ける。新しいゲームルールを推測して埋めない。

## 5. 差異台帳：そのまま流用しない項目

### D01 逐次手番の説明とSelect/Resolve

- 出典：A1§4「あなたの手番でやること」「マッチ」、B3§1・3・5・8。
- 確認事実：A1はタイムライン先頭で操作し、敵を攻撃するとマッチになると説明。B3は全必要スロットを確定して解決し、相互指定等で分類する。
- コード照合：[phase_flow.py](../../events/battle/phase_flow.py) は必要スロットのcommit数を確認して解決へ移行する。[DeclarePanel.js](../../static/js/battle/components/DeclarePanel.js) は「宣言／再宣言」を表示し、`battle_intent_commit` を送る。
- 判断：旧操作説明の訂正候補。公開側で別の「確定」ボタンがあるかのように書かず、「宣言を押して確定」と説明する。代表章の執筆時に通常モードの進行操作を画面確認する。
- 影響：R04・R05・O03。新しい裁定を決めずに編集を進められる。

### D02 戦闘開始時の全回復・FP初期化

- 出典：T「戦闘開始（セットアップ）」はHP・MP最大、FP0。B3§5.0とA2戦闘セッション追補は資源保持を記載。
- コード照合：[combat_session.py](../../manager/battle/combat_session.py) の `start_combat_session` と `conclude_combat_session` は戦闘一時状態を消去するがHP・MP・FPを回復・初期化しない。[test_combat_session_phase1.py](../../tests/test_combat_session_phase1.py) に開始・終結と状態保持の検証がある（未実行）。
- 判断：アプリの資源保持は確認できた。卓上の「毎遭遇で回復する規定」か「最初の準備状態の説明」かは文書だけで確定しない。基本本の共通ルールを変更する前に裁定の確認が必要。
- 影響：R04・O06。操作ガイドには自動全回復とは書かない。試作では初期値を明示した一遭遇に限定できる。

### D03 探索の標準式とUI初期値

- 出典：T「基本式」は1d6＋技能。[exploration_dock.js](../../static/js/exploration/exploration_dock.js) の `exp-roll-dice-count` 初期値は2で、選択値を送信。[socket_exploration.py](../../events/socket_exploration.py) も `dice_count` 欠損時の既定値は2。
- 判断：通常画面の初期値とルール本文の不一致を確認。UIが可変ダイス数を持つこと自体を不具合とは断定しない。標準ルールを適用する操作例では1を指定し、既定値の修正は別の実装判断として扱う。
- 影響：R03・O03。画面を開いてそのまま判定する例は使用しない。

### D04 初期作成時の輝化取得

- 出典：A3「ビルドの基本」は初期輝化を不可とする。T第四章「初期取得の考え方」は通過点があれば初期取得も可能と説明。
- 判断：文書間の相違。新規PCの標準初期通過点、シナリオ指定の例外、継続PC再編集を切り分ける必要がある。APIで保存可能なことだけでは卓上ルールの許可を確定できない。
- 影響：R02・R07。初回試作は輝化なしのPCで進め、公開時の許可条件は確認事項として残す。

### D05 ラティウムのFP獲得確率

- 出典：A1「ラウンド参加時の自動効果」はFP+1のみ記載。T「HP・MP・FPの自然変動」は50%と記載。
- コード照合：[common_manager.py](../../manager/battle/common_manager.py) のラティウム処理は `random.random() < 0.5` の場合にFPを1加算。
- 判断：A1の確率条件の記載不足。公開原稿では常時獲得と説明しない。その他の出身ボーナスは本件から類推せず、採用するものを個別照合する。
- 影響：R02・R06・R09。出身ボーナス表はそのまま転載しない。

### D06 不発とコストの包括表現

- 出典：T「不発の扱い」はコストを払わないと包括的に説明。B3§8は通常解決時の支払いと、広域のResolve開始時先払いを区別する。
- 判断：すべての不発を同じ支払条件で説明できるか未確認。今回は返金経路を網羅しておらず、広域不発時に返金されないと断定しない。宣言不能／防御対回避／対象消失／支払済みの広域を分けて処理経路を追う必要がある。
- 検証候補：[test_resolve_effect_cost.py](../../tests/test_resolve_effect_cost.py) と広域・単体解決処理。テストを読んだだけで全ケースを保証しない。
- 影響：R05・R09。基本マッチの例は進められるが、包括的な早見表の確定は照合後。

### D07 成長で使える経験の用途

- 出典：T「継続と成長」はシナリオ経験を新たな戦闘スキル取得用として説明。A1追補・F Part 9にはパラメータ成長もある。
- コード照合：[owned_characters.py](../../routes/owned_characters.py) は `param_increases` を受け、増加量の合計をスキル取得コストと合わせて経験予算から差し引く。
- 判断：基本本の説明が実装された成長用途を網羅していない。対象能力、上限、出身補正、再編集時の予算を照合して追記候補を作る。卓上での成長許可範囲は実装と別に確認する。
- 検証候補：[test_owned_character_growth.py](../../tests/test_owned_character_growth.py)。今回は内容の一部を確認し未実行。
- 影響：R07・O04。

### D08 HP0後の扱いと世界観の確定状況

- 出典：T「HP0と戦闘後処理」「継続と成長」は死亡・回復等をシナリオまたは運用に委ね、未定との記述がある。Discord未確認。
- 判断：「未記載だから死亡」「アプリで復帰できるから死亡しない」と補完しない。公開本に残す裁量の範囲と、共通裁定として確定させる範囲を確認する。
- 影響：R07・R08、GMの終了後手順。世界観全体の確定を他章の着手条件にはしない。

### 10.2 探索ダイス（D03更新）

- ルール本は1d6＋技能レベル。
- [探索画面](../../static/js/exploration/exploration_dock.js) の `exp-roll-dice-count` は初期値2、HTML上は最小1・最大10。実行時は入力したダイス数を送る。

### 10.3 能力値成長（D07更新）

| 観点 | 確認結果 |
| --- | --- |
| APIの機能 | `grow_owned_character` は正の `param_increases` を受け、増加量合計を経験コストとして扱う。docstringではhouse ruleと記載 |
| 対象能力 | ラベルの正規化は行うが、成長対象ラベルの許可リストはない。既存ラベルは加算、未知ラベルは新しく追加する |
| 上限 | この成長APIには能力値ごとの上限チェックがない。消費額と残り経験予算の比較はある |
| 予算 | 戦闘スキル追加と能力値増加は経験予算を共有。能力値消費はgrowth_logから累計する。輝化は通過点の別予算 |
| 派生値 | 成長APIの加算処理には、筋力等の変更からHP・MP・各補正を再計算する処理がない。キャラ作成ツール側の算出機能と区別する |
| 現在の成長画面 | `_pending` は戦闘スキルと輝化を保持し、送信payloadも `add_skill_ids` と `add_radiance_ids` のみ。能力値増加をこの画面から送る導線は確認できない |

出典：[成長API](../../routes/owned_characters.py) の `grow_owned_character`・`compute_param_growth_spent`、[成長画面](../../static/js/modals/owned_characters_modal.js) の「成長を適用」、[キャラ作成ツール](../../CharaCreator/GEMDICEBOT_CharaCreator.html) の `calculateStats`。

**結論**：前回の「実装にある能力値成長を基本本へ追記」という見立てを補正する。APIが受理する内容を共通ルールや完成した画面機能と見なさない。操作ガイドの成長画面は戦闘スキル・輝化の取得を説明し、能力値成長は許可範囲・上限・費用・派生値更新・実際の操作方法が決まるまで共通手順へ載せない。

入力制限がないことは「任意の項目を自由に成長させてよい」というルールではない。能力値成長を採用する場合はAPIの対象制限と派生値整合も実装課題として扱う。
