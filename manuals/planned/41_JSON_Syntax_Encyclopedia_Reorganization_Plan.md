## 1. 目的

スキル、パッシブ、バフ、召喚テンプレートのJSONについて、次の疑問をC01だけで解決できる状態を作る。

- JSONを上からどの順番で読めばよいか。
- 各キーは何を意味し、どこへ書けるか。
- 指定できる`timing`、`type`、`target`、`condition`には何があるか。
- 「タグ」という言葉が、`tags`、`tag_ids`、`required_tag_ids`でどう違うか。
- 作りたい効果を、どの記法の組み合わせで表現すればよいか。
- JSONが動かないとき、どこを確認すればよいか。

JSON定義の正本は引き続き`C01_JSON_Definition_Master.md`とする。図鑑用に同じ仕様を複製した別マニュアルは作らず、C01そのものを読みやすいリファレンスへ再編する。

## 2. 現状の課題

現在のC01には実装済み仕様が蓄積されているが、追加順に節が並んでおり、初めて読む人が必要な記法へ到達しにくい。

- JSON自体の基礎記法と、Gem_DiceBotTool固有のキーが同じ階層で説明されている。
- `timing`、`type`、`target`、`condition`の一覧が複数節へ分散している。
- 各effectの必須キー、任意キー、既定値、使用可能な対象が一覧で分からない。
- `tags`とキャラクターの`tag_ids`が、名前の近さに対して用途が異なる。
- スキル、パッシブ、バフ、召喚テンプレートでJSONの外枠が異なるが、入口で区別しにくい。
- 実装詳細はB01/B02にもあり、C01との役割分担が読み手に伝わりにくい。
- 自然言語JSONビルダーが生成できる記法と、手書き専用の記法が明示されていない。

## 3. 文書構成の基本方針

C01を次の4層構造へ再編する。

1. **はじめて読む**: JSONの基礎と、1件のスキルJSONを読む順番。
2. **キーを調べる**: キー、許容値、型、必須性、既定値を引く図鑑。
3. **目的から探す**: 「バフを付けたい」「対象のタグで分岐したい」などの用途別レシピ。
4. **問題を直す**: lint、自然言語ビルダー、キャッシュ確認、典型的なエラー。

戦闘処理の内部順序や実装経路はB01/B02を正とし、C01では「入力データとして何を書けるか」に集中する。

## 4. 図鑑の共通記載形式

各キー・列挙値は、可能な限り次の形式へ統一する。

| 項目 | 記載内容 |
|---|---|
| 名前 | 実際のJSONキーまたは列挙値 |
| 種別 | 文字列、数値、真偽値、配列、オブジェクト |
| 使用場所 | スキル直下、`effects[]`内、`condition`内など |
| 必須性 | 必須、条件付き必須、任意 |
| 許容値 | 使用可能な列挙値または値の範囲 |
| 既定値 | 省略した場合の挙動 |
| 意味 | プレイ上の効果 |
| 制約 | 組み合わせ不可、対応timing、対象制限 |
| 最小例 | そのままコピーできる1行JSON |
| 失敗時 | lintエラー、不発、安全な既定値など |
| 実装根拠 | バリデータ、effect handler、対象解決コード |

## 5. 収録する図鑑

### 5.1 JSON基礎

- オブジェクト`{}`
- 配列`[]`
- 文字列、数値、`true`/`false`、`null`
- ダブルクォート、コロン、カンマ
- ネストと読み下し方
- 1行JSONと整形JSONの使い分け
- 全角記号や末尾カンマなどの典型的な構文エラー

### 5.2 データ種別ごとの外枠

- スキル特記JSON
- 特殊パッシブの効果JSON
- バフ図鑑の効果JSON
- 召喚テンプレートの特記JSON
- `special_buffs[].data`のインライン効果

どのシートのどの列へ書くか、`schema`が必要か、ID参照か効果本体かを比較表にする。

### 5.3 スキル直下のキー

- `schema`
- `id`
- `tags`
- `target_scope`
- `power_bonus`
- `cost`
- `effects`

### 5.4 effect共通キー

- `timing`
- `type`
- `target`
- `condition`
- `value`
- `data`
- `lasting`
- `delay`
- `rounds`
- `repeat_count`
- type固有キー

### 5.5 `timing`図鑑

公開JSONで使用できるtimingを、実際の実行順に並べる。

- コスト・宣言前後
- マッチ前後
- 勝敗確定時
- Resolve開始時
- 的中・ダメージ適用前後
- ラウンド境界
- 即時・死亡時

各timingについて、発動回数、draw時の扱い、Select/Resolve限定か、自然言語ビルダーで生成できるかを併記する。内部境界名は公開記法と分離する。

### 5.6 `type`図鑑

実装済みeffect typeを、用途別に分類する。

- 状態・バフ: `APPLY_STATE`、`APPLY_BUFF`、`REMOVE_BUFF`など
- 威力・ロール補正: `DAMAGE_BONUS`、`MODIFY_BASE_POWER`、`MODIFY_FINAL_POWER`など
- リソース: FP、MP、HP、スタックの増減
- 行動経済: `USE_SKILL_AGAIN`、`GRANT_SKILL`
- 召喚・予約: `SUMMON_CHARACTER`、`SCHEDULE_EFFECT`
- フィールド集計: `APPLY_BUFF_FROM_CHARACTER_COUNT`
- 特殊処理: `CUSTOM_EFFECT`

typeごとに、必要な追加キー、対応target、対応timing、処理結果、最小例を記載する。

### 5.7 `target`と`target_scope`図鑑

次を明確に分ける。

- `target_scope`: スキル宣言時に誰を選べるか。
- effectの`target`: 効果を最終的に誰へ適用するか。

少なくとも、`self`、`target`、陣営全体、`KILLER`、`KILLER_TEAM`、`FILTERED_CHARACTERS`を収録する。対象不在時、死亡者・未配置・離脱者の扱いも記載する。

### 5.8 `condition`図鑑

- `source`
- `param`
- `operator`
- `value`

参照元、比較演算子、数値比較、文字列比較、配列の`CONTAINS`、状態異常、バフ、キャラクタータグ、`death_context`を一覧化する。未知値や型不一致がfalseになるケースも記載する。

### 5.9 タグとフィルター図鑑

- スキルの`tags`
- キャラクターの`tag_ids`
- `disabled_tag_ids`
- `required_tag_ids`
- `excluded_tag_ids`
- `character_filter.team`
- `alive`
- `placed`

「タグが存在する」と「有効タグとして条件に一致する」の違いを例示する。

### 5.10 `power_bonus`と`cost`図鑑

- `operation`
- `apply_to`
- 固定値、倍率、Nごと、条件付き補正
- FP/MP/HPなどのコスト
- 基礎威力と最終威力の違い

数値バランスの推奨値はF02へ委ね、C01では計算上の意味だけを扱う。

## 6. 用途別レシピ

完成例は、説明用の整形JSONと、スプレッドシート用の1行JSONを対にする。

- 的中時に状態異常を付与する
- 条件成立時だけ追加ダメージを与える
- キャラクタータグを条件にする
- 味方・敵の両方を選択可能にする
- バフ図鑑のバフを一定ラウンド付与する
- 次ラウンドから有効なバフを付与する
- 召喚キャラクターへタグとパッシブを持たせる
- 行動しないが攻撃可能な戦闘オブジェクトを作る
- 死亡原因となったキャラクターや陣営へ効果を返す
- 次ラウンド開始時に召喚する
- フィールド上の条件一致数を威力へ変換する
- 条件一致キャラクターを一括処理する
- 最大HPと同値のダメージを与える

シナリオ固有例はC01 §16を再利用し、同じJSONを別節へ複製しない。

## 7. エラー診断

症状から確認箇所を引ける表を作る。

| 症状 | 主な確認先 |
|---|---|
| `--update`が失敗する | JSON構文、`schema`、必須キー、参照ID |
| スキルは使えるが効果が出ない | `timing`、`condition`、対象、type固有キー |
| 味方・敵を選べない | `target_scope` |
| タグ条件が成立しない | `tag_ids`、`disabled_tag_ids`、完全一致 |
| バフが1ラウンドずれる | `lasting`と`delay` |
| 召喚されない | テンプレートID、実行timing、予約ラウンド |
| 自然言語変換に失敗する | 対応文型、禁止語彙、テンプレート名の完全一致 |

確認コマンド、対象キャッシュ、lint出力の読み方も併記する。

## 9. 実施順序

### Phase 1: 実装棚卸し

1. 公開可能な`timing`、`type`、`target`、condition source/operatorをコードから抽出する。
2. バリデータが許容するキーと、実行時コードが処理するキーを突き合わせる。
3. 自然言語ビルダー対応、手書き専用、内部専用へ分類する。
4. C01、B01、B02の重複と矛盾を一覧化する。

### Phase 2: C01の入口を再編

1. 冒頭へ読者別導線と目次を追加する。
2. JSON基礎とスキルJSONの読み方を最初へ移す。
3. スキル、パッシブ、バフ、召喚テンプレートの外枠を比較する。
4. 既存アンカーを極力維持し、他文書からのリンク切れを防ぐ。

### Phase 3: キー図鑑を作成

1. §5の各図鑑を共通形式で作る。
2. type固有キーと使用可能なtiming/targetを表にする。
3. 未対応・内部専用・非推奨記法を通常の許容値と分離する。
4. B01/B02の内部仕様へ必要な箇所だけリンクする。

### Phase 4: レシピとエラー診断

1. §6の用途別レシピを追加する。
2. 各例に整形版と1行版を用意する。
3. §7の症状別診断表を追加する。
4. `--update`、lint、キャッシュ確認の最短手順を固定する。

### Phase 5: 継続同期の仕組み

1. 実装済み列挙値と文書収録値の差を検出できる軽量テストまたは監査スクリプトを検討する。
2. 自動生成する場合もC01本文を直接上書きせず、差分確認用レポートを標準出力する。
3. 新しいeffect typeを追加したときに、C01と関連テストを更新するチェック項目をF01へ追記する。

### Phase 6: 検証

1. 全リンク、見出し、コードフェンスを確認する。
2. JSON例をパースし、skill rule v2の例はstrictバリデータへ通す。
3. 記載したIDを現行キャッシュと照合する。
4. 文字コード、文字化け、行末空白を検査する。
5. 文書だけでは判定できない記法を「未確認」として残し、推測で対応済みにしない。

## 10. 受け入れ条件

- [ ] 初見の読者が、JSONの基本構造とスキルJSONの読み順をC01だけで理解できる。
- [ ] 実装済みの公開`timing`、`type`、`target`、condition演算子が図鑑から検索できる。
- [ ] 各記法について、型、使用場所、必須性、既定値、制約、最小例が分かる。
- [ ] `tags`、`tag_ids`、`required_tag_ids`の違いが明確である。
- [ ] スキル、パッシブ、バフ、召喚テンプレートのJSONを混同しない構成になっている。
- [ ] 自然言語ビルダー対応と手書き専用記法を区別できる。
- [ ] 主要な作成目的からコピー可能な作例へ到達できる。
- [ ] lint失敗と「構文は正しいが発動しない」を切り分けられる。
- [ ] C01とB01/B02で同じ仕様を重複定義せず、正本の責務が明確である。
- [ ] 掲載したJSON例がパース・バリデーションを通る。

## 11. 対象外

- スキル威力やコストの妥当性判断。F02の担当とする。
- 未実装effectの新規設計。
- JSONビルダーUIそのものの刷新。
- Google Sheetsの列構成変更。
- シナリオ固有の行動チャート作成。

## 12. 最初に着手する作業

Phase 1で実装値を棚卸しし、「実装済み・自然言語生成対応・手書き専用・内部専用」の4区分表を作る。その表を確定してからC01の大規模な並べ替えへ進む。
