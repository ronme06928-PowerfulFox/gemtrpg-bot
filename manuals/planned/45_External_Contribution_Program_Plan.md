## 1. 目的

Discordサーバーの数人程度の協力者が、リポジトリもスプレッドシートも触らずに、シナリオ用のコンテンツを制作してセッションで使える状態を作る。

制作物の受け渡し、品質の担保、権利とクレジットの扱いを事前に決め、制作の相談が来るたびに毎回口頭で説明する状態をなくす。

## 2. 前提と基本方針

1. マスターデータの正本は Google Sheets のまま維持する。外部から直接書き込む経路は作らない。
2. 寄稿物を**アプリ内で完結する Tier A** と、**マスターデータである Tier B** に二分する。本計画の実装対象は Tier A のみとする。
3. Tier A の制作・検証・受け渡しに必要なUI、戦闘機能、DB永続化は実装済みである。本計画で追加するのは**文書と運用ルールのみ**とし、アプリのコード変更を含めない。
4. 協力者は本番アプリに各自のアカウントを作り、**自分がownerのルーム**で制作と実機確認を行う。ローカル環境の構築を要求しない。
5. 既存の権限・ACL・検証機構を流用し、寄稿者向けの新しい共有経路や新しい検証経路を作らない。

## 3. 対象範囲

### 3.1 Tier A（本計画の対象・承認不要で制作可能）

| 制作物 | 保存先 | 制作手段 | 参照仕様 |
| --- | --- | --- | --- |
| 敵・NPCキャラクター | 戦闘専用プリセット v3（ユーザー所有） | `CharaCreator/GEMDICEBOT_CharaCreator.html` でJSON生成しアプリへ投入 | `E02` Part 5 |
| キャラクタータグ | キャラクターJSON内 | CharaCreator（`characterType=scenario`） | `C01` §13 / `E02` Part 7 |
| 敵行動チャート | キャラクターの `behavior_profile` | アプリ内の行動チャート編集UI | `D01` Part 1 §6 / `E02` Part 9 |
| 編成（味方・敵） | プリセット v3 | 戦闘専用プリセット管理ワークスペース | `D01` Part 4 / `E02` Part 10 |
| ステージ・ステージ効果 | プリセット v3 | 同上 | `D01` Part 3 |
| コレクション・区分 | プリセット v3 | 同上 | `D01` Part 4 §1 |
| シナリオ本文・GM資料 | 外部文書（Markdown / PDF） | 任意のエディタ | なし |
| 持ちキャラ | アカウント | CharaCreator＋成長画面 | `F01` Part 9 / `E02` Part 6 |

### 3.2 Tier B（本計画では文書のみ・受付は将来）

スキル、バフ図鑑、特殊パッシブ、召喚テンプレート、アイテム、用語図鑑、輝化スキル。いずれも Google Sheets が正本であり、反映には `python app.py --update` と push が必要なため、外部から独立して追加できない。

本計画では「Tier B は現在受け付けていない」ことと、必要になった場合の相談窓口だけを文書化する。受付を開始する場合は §9 の将来拡張へ従う。

### 3.3 対象外

- Python コード、フロントエンド JS、CSS、DBスキーマの変更
- `CUSTOM_EFFECT` の新しい実装名、`plugins/buffs/` のバフプラグイン追加
- 未実装 effect type の新規設計
- 寄稿者へのリポジトリ配布、`data/cache/*.json` の配布
- 寄稿専用のアップロードUI、投稿フォーム、レビュー管理画面
- 全ユーザー向けのコンテンツ公開マーケット

## 4. 制作から反映までのフロー

プリセットのDB永続化と環境分離は実装済みであり、次のフローで本番制作を開始できる。シナリオ単位の受け渡しにはコレクションの移送JSONを使用する。

```text
協力者                                        管理者（リポジトリ所有者）
  |  1. 本番アプリでアカウント作成
  |  2. 自分のルームを作成（作成者は自動でowner）
  |  3. CharaCreator でキャラクターJSONを作成
  |  4. 自分のルームへ投入し、タグと行動チャートを設定
  |  5. プリセットへ保存し、編成とステージを組む
  |  6. 戦闘専用モードで実機確認（自分がownerなので自由に試せる）
  |  7. プリセット管理から Export でJSONを出力
  +----- 8. Discord へ Export JSON と設計メモを添付 ----->|
  |                                                       |  9. 形式確認（Import が通るか）
  |                                                       | 10. 妥当性確認（F02基準・世界観・重複）
  |<---- 11. 差し戻し（理由コード付き）------------------+
  |                                                       | 12. 本番ルームへ Import
  |                                                       | 13. CONTRIBUTORS.md へ追記
  |<---- 14. 反映報告 -----------------------------------+
```

Import 時に検証エラーとなったJSONは保存されない既存挙動（`A02` 追補 2026-02-26）をそのまま形式チェックとして使う。寄稿者向けに新しい検証コマンドは用意しない。

## 5. 制作物の受け渡し

- 受け渡しは**プリセット Export JSON を Discord に添付**する方式を正とする。
- アプリ内の共有ACLによる受け渡しは、グローバルな個別ユーザー共有が未実装（計画42・43が未接続）のため、初期運用では採用しない。同じルームへ一時的に招く運用が必要になった場合のみ、参加コードとGM PINで対応する。
- Export JSON はファイル名に制作物名と日付を含めてもらう。Discord上に履歴が残ることを、変更管理の代わりとして許容する。
- 画像は Cloudinary 運用ルール（`F01` Part 1-C）に従う。寄稿者が直接アップロードした画像の公開範囲は、既存の画像公開設定に従う。

## 6. 相談が必要な範囲（線引き）

既存スキル・既存バフの組み合わせで表現できる範囲は、事前相談なしで自由に制作してよい。

次の場合は制作前に管理者へ相談する。

- 新しい敵専用スキル（`E-` 系）が必要になった場合
- 新しいバフ、状態異常、パッシブ、召喚テンプレートが必要になった場合
- 既存の効果では表現できない挙動を求める場合

この線引きにより、Tier B が必要になる場面が自然に相談として上がってくる。

## 7. 受け入れ基準と差し戻し理由コード

差し戻し時は理由コードを添えて返す。文書 `04_Review_Criteria.md` に一覧を載せる。

| コード | 意味 | 主な確認先 |
| --- | --- | --- |
| `R-IMPORT` | Import が通らない。JSON構造または参照IDの不整合 | `A02` 追補 2026-02-26 §2 |
| `R-BALANCE` | 敵の威力・HP・行動回数が遭遇設計の相場から外れている | `F02` 戦闘遭遇・シナリオ設計ガイド |
| `R-CHART` | 行動チャートが停止・空振り・無限ループする | `D01` Part 1 §6 |
| `R-DUP` | 既存キャラクター・編成・ステージと実質的に重複 | 既存プリセット |
| `R-SCOPE` | 対象外（コード変更や新規effectを要求している） | 本書 §3.3 |
| `R-LORE` | 世界観・設定と整合しない | 卓上ルール本（`typst_manual/全体マニュアル`） |
| `R-RIGHTS` | 画像・文章の権利関係が不明 | 本書 §8 |
| `R-UNTESTED` | 寄稿者の実機確認が行われていない | 本書 §4 手順6 |

## 8. 権利・クレジット

- 寄稿者は、提出物をこのアプリおよびシナリオで利用・改変・再配布することへ同意する。同意は提出時にDiscord上で明示的に確認する。
- 第三者の画像・文章・設定を含める場合は、出典と利用可否を提出時に申告する。不明なものは受け付けない（`R-RIGHTS`）。
- クレジットは次の2か所へ記載する。
  1. `manuals/contrib/CONTRIBUTORS.md`（氏名またはハンドル、貢献内容、日付）
  2. 該当シナリオ本文の巻末（「データ協力」欄）
- アプリ内の「このアプリについて」画面は現時点で存在しないため、初期実装では作らない。協力者が定着し、アプリ内表示が必要になった時点で別計画とする。
- プリセット v3 は所有者・編集者・閲覧者を表示するため、Tier A の制作物については制作者がアプリ内にも実質的に表示される。この既存表示をクレジットの一部として扱う。
- 寄稿の撤回を求められた場合は、該当プリセットをアーカイブし、CONTRIBUTORS.md の記載を削除する。既に公開したシナリオ本文からの遡及削除は約束しない。この方針を提出前に明示する。

## 9. ネタバレの扱い（確認済みの前提）

`/api/get_skill_data`、`/api/get_buff_data`、`/api/get_passive_data`、`/api/get_glossary_data` は認証も権限確認もなくマスターデータ全体を返す（`app.py`）。したがって「敵専用スキルを渡さないことでネタバレを防ぐ」対策は、寄稿者に限らず全プレイヤーに対して既に成立していない。

一方、シナリオ構成（どの敵をどう組み合わせ、どのステージで戦うか）はプリセット v3 のACLで保護されている。守るべき対象はスキルカタログではなくシナリオ構成であり、そこは既存機構で機能している。

本計画は Tier A のみを対象とし、寄稿者はアプリ内で作業するため `data/cache/*.json` の配布を行わない。よってネタバレ対策として新たな実装は行わない。Tier B の受付を開始する場合のみ、検証用データ配布の是非を改めて判断する。

## 11. 実装段階

### Phase 1: 文書骨格

1. `manuals/contrib/` を作成し、`README.md` に役割と境界（§3・§6）を書く。
2. `04_Review_Criteria.md` と `05_Rights_And_Credits.md` を書く。提出前に合意しておく内容なので制作ガイドより先に固める。
3. `CONTRIBUTORS.md` を空の表として作る。

### Phase 2: シナリオ制作ガイド

1. `01_Scenario_Authoring_Guide.md` を、実際にアプリを操作しながら画面順に記述する。
2. 既存仕様の複製ではなく、手順＋該当仕様へのリンクで構成する。数値基準は `F02` へリンクし転記しない。
3. 記述した手順を、管理者以外の視点で1度通しで実行して詰まる箇所を洗う。

### Phase 3: 導線の接続

1. `manuals/README.md` に `contrib/` 系統を追記する。
2. 計画46で作る読者別入口（`START_HERE.md`）から `contrib/README.md` へ導線を張る。
3. `A02` に「外部協力者へ制作を依頼する場合」の1節を追加し、`contrib/` へリンクする。

### Phase 4: 初回運用と反映

1. 協力者1人に Phase 2 のガイドだけを渡し、質問された箇所をガイドへ反映する。
2. 実際に受け取った Export JSON で §4 のフローを1周し、理由コードの不足を補う。
3. 初回反映後、`CONTRIBUTORS.md` を更新する。

## 12. 将来拡張（Tier B を開ける場合）

着手前に本節を独立した計画書へ切り出す。以下は判断材料としての見通しであり、本計画の実装対象ではない。

1. **`X-` 提案ID名前空間**: 提案段階のIDは `X-` 接頭辞で始め、採用時に管理者が正式IDを採番する。`lint` へ「本番キャッシュに `X-` を含むIDがあれば ERROR」を追加し、混入を検出できるようにする。
2. **Contribution Pack 形式**: 提出物を1つのJSONへまとめる。各エントリの形をスプレッドシートの列構成に一致させ、取り込みを転記作業にする。
3. **検証CLI**: `scripts/contrib_tool.py validate` を新設し、`manager/json_rule_v2`（strict）と `scripts/skill_catalog_tool.warn_catalog` を再利用する。寄稿者が記法エラーを自分で潰せる状態にすることが目的。
4. **計画41 Phase 1 の共用**: 41 Phase 1 が作る「実装済み・自然言語生成対応・手書き専用・内部専用」の4区分表は、そのまま「外部寄稿で使ってよい記法の定義」になる。Tier B の記法ガイドはこの表を正本として参照し、複製しない。41 Phase 2 以降（C01本体の再編）は Tier B の前提ではない。
5. **サンドボックス取り込み**: 寄稿者が自分のルームで新スキルを実際に動かせるようにする案。`all_skill_data` はグローバル辞書として約25の本番モジュールから直接参照されているため、ルーム別オーバーレイには解決経路を関数へ集約する改修が必要。実施する場合は「戦闘専用モード限定・GM権限者のみ・その戦闘中だけ有効」まで範囲を絞り、独立した計画書を立てる。
