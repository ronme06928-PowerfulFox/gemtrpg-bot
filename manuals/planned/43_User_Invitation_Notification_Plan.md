## 1. 目的

ログインユーザーが内部UUIDやログイン名を公開せずに相手を指定し、ルームへの招待、権限変更、プリセット共有など、自分に関係する出来事をロビーから確認・処理できる共通基盤を作る。

ルーム招待は「通知を表示した」という履歴だけでは成立しない。招待の保留・承認・辞退・取消・期限切れを管理する業務データと、ユーザーごとの通知・未読状態を別々に永続化する。

通知の正本はDBとし、Socketはオンライン中に新着を早く知らせる配送手段としてだけ使う。オフライン、再接続、複数端末でも通知を失わないことを優先する。

## 2. 現状

- `User.id`はUUIDであり、他ユーザーへ安全に見せられる短い公開コードはない。
- 表示名`User.name`は重複可能であり、招待相手の一意指定には使えない。
- 公開ルームは参加コードの検証に成功すると、その場で`RoomMember`が作られる。承認待ちの招待状態は存在しない。
- `RoomMember`はowner・gm・playerと失効履歴を管理できるため、招待承認後の参加状態には引き続き利用できる。
- `RoomLogArchive`はルームログの保全用であり、未参加ユーザーへの個人通知、未読状態、招待操作には流用できない。
- 認証済みSocketはロビー表示中も接続を維持しているが、ユーザー単位の通知配送roomはない。
- ロビーにはルーム一覧とユーザー設定があるが、通知一覧・未読件数・招待応答UIはない。
- GM付与、GM解除、除名、オーナー移譲は処理結果を対象ユーザーのロビーへ通知しない。

## 3. 対象範囲

### 3.1 初期実装に含める

- 内部UUIDとは別の公開ユーザーコード
- 公開ユーザーコード完全一致による限定検索
- 同じルームのメンバーから共有先を選ぶ補助候補
- ルームowner・gmからユーザーへのルーム招待
- 招待の承認、辞退、取消、期限切れ
- ユーザーごとの通知ログ
- 未読件数、個別既読、すべて既読、アーカイブ
- ロビーの通知ボタン、未読バッジ、通知一覧、招待操作
- ユーザー専用Socket roomによる新着・更新通知
- ルーム権限変更とプリセット共有から通知を作る共通サービス
- 招待乱用とユーザー列挙を抑える回数制限

### 3.2 初期実装に含めない

- 全ユーザーを閲覧できる公開名簿
- 表示名の無制限な部分一致検索
- フレンド、フォロー、ブロック、ダイレクトメッセージ
- メール、Web Push、OS通知、外部サービスへの通知
- 通知本文から任意URLや任意JavaScriptを実行する仕組み
- 戦闘中の手番・宣言待ち通知
- 管理者が全ユーザーの個人通知を閲覧する機能
- 通知ログをセキュリティ監査ログの代わりにすること

## 4. 基本方針

1. 招待状態は`room_invitations`、表示履歴と未読状態は`user_notifications`へ分離する。
2. 通知はDBを正本とし、Socketイベントだけに依存しない。
3. 通知本文を自由記述だけで保存せず、登録済み`type`と構造化`payload`から表示を組み立てる。
4. 通知の宛先、招待対象、ルーム、操作権限はサーバー側の認証ユーザーとDBから判定する。
5. 内部UUID、ログイン名、所属ルーム一覧、最終ログインなどをユーザー検索結果へ含めない。
6. 公開ユーザーコードは検索用識別子であり、DB内の所有権・membership・ACLは引き続き`User.id`を使う。
7. 招待承認と`RoomMember`作成は同じDBトランザクションで行う。
8. Socket通知はDB commit後に送る。Socket送信に失敗してもDB上の通知は残す。
9. 同じ操作の再試行で招待や通知が重複しないよう、一意制約と重複防止キーを持たせる。
10. アプリ管理者権限はルーム管理の復旧には利用できるが、個人通知の一括閲覧権限にはしない。

## 5. 公開ユーザーコードと限定検索

### 5.1 保存項目

`User`へ次を追加する。

- `public_user_code`: 表示用の短いコード
- `public_user_code_normalized`: 検索・一意制約用の正規化値
- `public_user_code_updated_at`: 再発行管理用

コードは次の性質を持たせる。

- 8〜10文字程度の推測困難なランダム値
- 大文字小文字を区別しない
- `0/O`、`1/I/L`など見間違えやすい文字を除いたBase32系文字集合
- 連番やUUIDの先頭切り出しを使わない
- DB一意制約で衝突を防ぎ、衝突時は再生成する
- 既存ユーザーにはmigrationまたは起動時移行で一度だけ割り当てる
- 再発行しても内部`User.id`、既存membership、既存ACLは変えない

### 5.2 検索範囲

初期実装では次だけを候補にする。

- 入力された公開ユーザーコードへの完全一致
- 対象ルームの有効な`RoomMember`

完全一致検索の応答は公開ユーザーコードと表示名だけを返す。存在しない場合と検索回数制限中の応答は、不要なアカウント列挙を助長しない文面にする。

検索、招待送信、短時間の再送にはユーザー単位・送信元IP単位の回数制限を設ける。検索結果をページング可能な全ユーザー一覧として返さない。

## 6. データモデル

### 6.1 `RoomInvitation`

| 項目 | 内容 |
| --- | --- |
| `id` | 外部へ渡しても連番を推測しにくいUUID |
| `room_id` | 招待先ルーム |
| `invitee_user_id` | 招待されたユーザー |
| `invited_by_user_id` | 招待したユーザー |
| `requested_role` | 初期実装は`player`を正とする |
| `status` | `pending` / `accepted` / `declined` / `revoked` / `expired` |
| `created_at` | 作成日時 |
| `expires_at` | 有効期限 |
| `responded_at` | 承認・辞退日時 |
| `revoked_at` | 取消日時 |
| `updated_at` | 状態更新日時 |

同じ`room_id`と`invitee_user_id`について、有効な`pending`招待を1件だけ許可する部分一意制約をSQLite・PostgreSQLの双方へ設定する。

初期実装ではルーム招待を`player`参加に限定する。GM付与は既存のowner専用操作として維持し、付与後に通知する。将来GM招待を承認式にする場合は`requested_role`を拡張する。

### 6.2 `UserNotification`

| 項目 | 内容 |
| --- | --- |
| `id` | 通知ID |
| `recipient_user_id` | 宛先ユーザー |
| `type` | 登録済み通知種別 |
| `actor_user_id` | 操作したユーザー。削除済みならnull可 |
| `room_id` | 関連ルーム。削除済みならnull可 |
| `entity_type` | `room_invitation`、`preset`など |
| `entity_id` | 関連データのID |
| `payload` | 表示に必要な最小限の構造化情報 |
| `dedupe_key` | 同じ出来事の重複作成防止キー |
| `created_at` | 作成日時 |
| `read_at` | 未読ならnull |
| `archived_at` | 通常一覧から隠す場合の日時 |

`recipient_user_id + dedupe_key`を一意にする。宛先と作成日時の降順、宛先と未読状態を効率よく検索できるindexを用意する。

通知行は宛先ごとに1件作成する。複数宛先を1行へまとめず、既読・アーカイブ状態を共有しない。

### 6.3 削除時の扱い

- ユーザー削除時は、そのユーザー宛通知を削除する。
- 操作者が削除されても通知は残し、`actor_user_id`をnullにする。
- ルーム削除時は保留招待を無効化し、通知の`room_id`はnullにして表示用スナップショットを残す。
- 通知`payload`へルーム秘密情報、参加コード、GM PIN、内部UUIDを保存しない。

## 7. 通知種別

初期登録する通知種別を次に限定する。

| `type` | 宛先 | 操作 |
| --- | --- | --- |
| `room.invited` | 招待されたユーザー | 承認・辞退 |
| `room.invite_accepted` | 招待者 | 結果確認 |
| `room.invite_declined` | 招待者 | 結果確認 |
| `room.invite_revoked` | 招待されたユーザー | 状態確認 |
| `room.role_granted` | 権限を付与されたユーザー | ルーム確認 |
| `room.role_revoked` | 権限を解除されたユーザー | 状態確認 |
| `room.member_removed` | 除名されたユーザー | 状態確認 |
| `room.owner_transferred` | 新旧オーナー | 状態確認 |
| `preset.shared` | 共有されたユーザー | プリセット確認 |
| `preset.share_revoked` | 共有解除されたユーザー | 状態確認 |
| `preset.ownership_transferred` | 新旧所有者 | 移譲結果確認 |
| `system.announcement` | 指定ユーザー | 内容確認 |

通知の操作ボタンは保存済みURLではなく、`type`、関連ID、現在のサーバー状態からAPI応答時に組み立てる。期限切れ・取消済み招待には承認ボタンを返さない。

通知種別ごとにpayload schemaを定義し、未知キーをそのままHTMLへ展開しない。表示名やルーム名はテキストとしてエスケープする。

## 8. ルーム招待フロー

### 8.1 招待作成

1. 対象ルームのownerまたはgmが公開ユーザーコードかルームメンバー候補から相手を選ぶ。
2. サーバーが送信者の最新`RoomMember`を検証する。
3. 自分自身、既存メンバー、同一の保留招待、存在しないユーザーを拒否または冪等応答にする。
4. `RoomInvitation(status=pending)`と`room.invited`通知を同一トランザクションで保存する。
5. commit成功後、対象ユーザーのSocket roomへ新着通知を送る。

owner・gmはplayer招待を作成できる。GM付与、owner移譲、メンバー除名など既存のowner専用操作は本計画によって緩和しない。

### 8.2 承認

1. 認証ユーザーが招待の`invitee_user_id`と一致することを確認する。
2. 招待が`pending`で、有効期限内で、対象ルームが存在することを確認する。
3. 同一トランザクションでplayerの`RoomMember`を作成し、招待を`accepted`へ更新する。
4. 招待者へ`room.invite_accepted`通知を作る。
5. commit後に双方の通知一覧・ルーム一覧を更新する。

既にmembershipが存在する場合は二重作成せず、招待を成立済みとして安全に収束させる。短時間の二重クリック、複数端末、再送で結果が変わらないようにする。

### 8.3 辞退・取消・期限切れ

- 辞退は招待対象者だけが実行できる。
- 取消は対象ルームのowner・gm、またはアプリ管理者が実行できる。
- 辞退・取消後は承認できない。
- 有効期限を過ぎた招待は取得・操作時に`expired`へ遷移させる。定期ジョブは初期実装の必須条件にしない。
- ルーム削除時は保留招待を無効化し、承認できないようにする。
- 招待者がGMからplayerへ降格しても、既に送った招待を自動承認しない。取消権限は現在のルームroleから再判定する。

### 8.4 参加コードとの併存

既存の参加コード方式は残す。

- 参加コード: `listed`ルームへユーザーが自分から参加する経路
- ルーム招待: hidden・closedを含むルームから特定ユーザーを招く経路

招待承認では参加コードを要求しない。招待の宛先ユーザー本人であることと、保留招待が有効であることを参加資格にする。

## 9. 通知API

具体的なURLは既存Blueprint構成に合わせて実装時に確定するが、次の契約を用意する。

### 9.1 ユーザー検索

- 公開ユーザーコード完全一致検索
- 対象ルームの有効メンバー候補取得
- 応答は公開ユーザーコード、表示名、用途別の選択可否だけ

### 9.2 招待

- 招待作成
- 自分宛保留招待一覧
- 対象ルームが送信した保留招待一覧
- 招待承認
- 招待辞退
- 招待取消

招待IDはクライアントから渡されても、宛先・対象ルーム・操作権限を毎回DBで再検証する。

### 9.3 通知

- cursor方式の通知一覧取得
- 未読件数取得
- 個別既読
- すべて既読
- 個別アーカイブ

一覧は`created_at`と`id`を組み合わせた安定cursorを使い、同時に新着が増えても重複・欠落しにくくする。通常一覧はアーカイブ済みを除外し、未読のみの絞り込みを許可する。

既読・アーカイブ操作は通知の宛先本人だけが実行できる。アプリ管理者であっても通常APIから別ユーザーの個人通知を取得しない。

## 10. Socket配送

認証済みSocket接続時に、サーバーが`user:{user_id}`形式のユーザー専用Socket roomへ参加させる。room名はサーバー側で作り、クライアント入力を使わない。

初期イベントは次とする。

- `notification_created`: 新着通知が作成された
- `notification_updated`: 既読、アーカイブ、招待状態が変わった
- `notification_unread_count`: 未読件数が変わった

Socket payloadは再取得に必要な通知IDと未読件数を中心にし、個人情報や完全な通知履歴をbroadcastしない。クライアントは新着イベントを受けたら必要に応じて通知APIから正本を取得する。

- 同一ユーザーの複数端末へ同じイベントを送る。
- Socket切断中に作られた通知は次回HTTP取得で復元する。
- Socket送信の成否でDB transactionをロールバックしない。
- 通知作成前に送信せず、必ずcommit後に送る。
- ロビーからルームへ入室してもユーザー専用Socket roomから離脱しない。

## 11. ロビーUI

ロビー上部のユーザー操作帯へ通知ボタンを置く。

```text
ようこそ、ユーザー名 さん            [通知 3] [ユーザー設定] [ログアウト]
                                          │
                                          └ 通知一覧
                                             ・未読のみ
                                             ・すべて既読
                                             ・招待を承認 / 辞退
                                             ・関連ルームを開く
```

### 11.1 一覧表示

- 未読件数を数字とテキストで示し、色だけに依存しない。
- 新しい順で表示し、追加読込を行える。
- 通知種別、発生時刻、操作者表示名、対象名、現在状態を表示する。
- 期限切れ、取消済み、削除済み対象は操作不能として理由を表示する。
- 一覧を開いただけでは全件を既読にしない。
- 通知を開いたときの個別既読と、明示的な「すべて既読」を用意する。
- 承認・辞退中はボタンを無効化し、二重送信を防ぐ。
- API失敗時は通知を消さず、再試行できる。

### 11.2 ルーム一覧との連携

- 招待承認後はルーム一覧を再取得し、対象ルームを参加済みとして表示する。
- hiddenルームでも、有効な招待通知から必要最小限のルーム名を確認できる。
- ルームが削除済みなら入室ボタンを出さない。
- ルーム内でも通知ボタンを表示するかは後続UI判断とし、初期実装の必須範囲はロビーとする。

## 12. 共通通知サービス

各ルートから`UserNotification`を直接組み立てず、共通サービスを設ける。

```text
create_user_notification(
  recipient_user_id,
  type,
  actor_user_id=None,
  room_id=None,
  entity_type=None,
  entity_id=None,
  payload=None,
  dedupe_key=None,
  commit=False,
)
```

共通サービスは次を担当する。

- 通知種別とpayload schemaの検証
- 宛先、関連ID、重複防止キーの正規化
- 重複作成時の冪等な既存通知返却
- DB保存と、commit後Socket配送用データの生成
- API向け安全DTOへの変換
- 既読・アーカイブの宛先本人確認

通知を発生させる元処理は、主処理と通知保存を同一トランザクションに含める。通知だけが失敗した場合に主処理を成功させるかは、処理種別ごとに決めず共通方針を採用する。初期方針は、ユーザーの権利状態が変わる招待・除名・共有では通知保存まで成功条件に含め、Socket配送だけをbest-effortとする。

## 13. 権限・プライバシー・乱用対策

- ユーザー検索、招待、通知取得はすべてログイン必須とする。
- 検索結果へ内部UUID、ログイン識別子、最終ログイン、所属ルーム一覧を返さない。
- 表示名が重複しても公開ユーザーコードで選択対象を確定する。
- 招待作成者が対象ルームの現在のowner・gmであることを毎回DBで確認する。
- 通知ID、招待IDの推測だけで他人の情報を取得・更新できないよう、宛先を必ず照合する。
- 自分自身への招待、既存メンバーへの招待、同一招待の連打を拒否または冪等化する。
- ユーザー検索と招待作成へ短時間・日単位の回数制限を設ける。
- 通知payload内の文字列をHTMLとして挿入せず、エスケープまたは`textContent`を使う。
- 参加コード、GM PIN、復旧コード、内部ACL全体を通知へ含めない。
- アプリ管理者の復旧操作は監査ログへ記録するが、個人通知の常時閲覧権限は与えない。

通知拒否、特定ユーザーのブロック、通知種別ごとのミュートは初期実装対象外とする。ただし乱用が確認された場合に追加できるよう、通知種別と送信者を構造化して保持する。

## 14. 保存期間

通知は無制限に増やさない。初期値は実装着手前に確定する。

推奨案:

- 既読かつアーカイブ済み通知: 180日後に削除可能
- 未読通知: 一律自動削除しない
- 完了済み招待: 1年間保持後に削除可能
- 保留招待: 有効期限経過後に`expired`へ遷移
- 法的・セキュリティ監査が必要な操作: 通知ログではなく別の監査ログ方針へ従う

定期削除ジョブがない初期段階では、一覧取得時に大量削除しない。管理用の明示的cleanupコマンドまたは軽量な定期処理として後から接続する。

- `models.py`

## 17. テスト計画

### 17.1 公開ユーザーコード

- [ ] 新規・既存ユーザーへ一意なコードを割り当てられる。
- [ ] 大文字小文字の違いを正規化できる。
- [ ] コード衝突時に既存ユーザーを上書きせず再生成する。
- [ ] 完全一致以外ではユーザーを返さない。
- [ ] 応答へ内部UUID、ログイン名、最終ログイン、所属ルーム一覧が混入しない。
- [ ] 検索と招待の回数制限がユーザー列挙・連打を抑止する。

### 17.2 招待状態

- [ ] owner・gmはplayer招待を作成でき、playerは拒否される。
- [ ] 自分自身、既存メンバー、存在しないユーザーへの招待を安全に処理する。
- [ ] 同じルーム・ユーザーの保留招待を二重作成しない。
- [ ] 招待対象本人だけが承認・辞退できる。
- [ ] owner・gmだけが保留招待を取り消せる。
- [ ] 承認時に招待更新と`RoomMember`作成が同じtransactionで完了する。
- [ ] membership作成失敗時に招待だけ`accepted`にならない。
- [ ] 二重クリック・複数端末・再送でmembershipが重複しない。
- [ ] 辞退・取消・期限切れ・削除済みルームの招待を承認できない。

### 17.3 通知

- [ ] 通知は宛先本人だけが取得・既読・アーカイブできる。
- [ ] アプリ管理者でも通常APIから他人の通知を取得できない。

- [ ] 個別既読、すべて既読、未読件数が一致する。
- [ ] アーカイブしても関連する招待状態は変化しない。

- [ ] 通知payloadへ秘密値と内部UUIDが混入しない。
- [ ] 不正な通知種別・payloadを保存できない。

### 17.4 Socket・複数端末

- [ ] 別ユーザーのSocketへ通知が漏れない。
- [ ] オフライン中の通知を次回ロビー表示で取得できる。
- [ ] Socket再接続後にDB取得で未読件数が収束する。

## 19. 計画42との境界

計画43は、公開ユーザーコード、共有先候補、安全なユーザー解決、ユーザー通知を提供する共通基盤である。

計画42は次だけを担当する。

- プリセットの`access_control`へ内部`user_id`を保存する
- 計画43のユーザー選択UI/APIから共有先を受け取る
- 個別共有・共有解除時に計画43の共通通知サービスを呼ぶ
- プリセット閲覧・利用・編集・ルーム配置の認可を行う
- プリセットをユーザー所有のグローバル資産として管理し、ルーム固有プリセットを作らない
- 管理者によるプリセット所有権移譲、孤立資産回収、ユーザー削除前検査を行う

公開ユーザーコードはプリセットACLへ保存しない。コードが再発行されても既存共有を維持するため、検索後に解決した内部`user_id`を保存する。

計画43は所有権移譲先の安全なユーザー解決と移譲通知を提供するが、プリセットの所有権変更、孤立判定、ユーザー削除可否は計画42の責務とする。

計画42のワークスペース骨格・一覧・編成編集は計画43より先に実装できる。ただし、グローバルな個別ユーザー共有UIと共有通知は、計画43のユーザー解決・通知基盤が完成するまで未接続とする。同じルームの既存メンバーだけを選ぶ暫定実装を行う場合も、後から公開ユーザーコード解決へ置換できる境界を保つ。

## 20. 受け入れ条件

- 内部UUIDやログイン名を公開せず、公開ユーザーコードで招待相手を一意に指定できる。
- 全ユーザー一覧を公開せず、完全一致検索と同じルームのメンバー候補だけを利用できる。
- ルーム招待が承認されるまで`RoomMember`を作らない。
- 招待の承認・辞退・取消・期限切れが通知表示とは独立した状態として保存される。
- オフライン・再接続・複数端末でも通知と未読件数をDBから復元できる。
- ロビーで通知一覧、未読件数、招待承認・辞退を操作できる。
- 通知や招待を他人が取得・更新できず、秘密値や内部識別子が応答へ漏れない。
- 重複送信、二重クリック、Socket失敗、DB失敗で招待・membership・通知が矛盾しない。
- 既存の参加コード方式、ルーム権限、ルーム一覧を破壊しない。
- 計画42が同じユーザー解決・通知基盤を利用し、プリセット独自のユーザー検索を重複実装しない。
- 実装後、現在仕様を既存正本へ統合し、本計画書を削除できる。
