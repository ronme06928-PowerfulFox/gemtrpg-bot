# 保存・復元の確認手順

対象: アプリ基盤プロジェクト `OPS-RECOVERY` と `OPS-RECOVERY-LOCAL`。ローカルSQLiteの保存・復元検証と、本番Neonの画面確認を管理する。2026-11-01には合成データのPostgreSQLバックアップ・別DB復元も検証した。11/1 00:48 JSTにユーザーが初回バックアップを取得し、再検査も成功した。本番バックアップからの実DB復元とRenderの終了動作は未確認。

## 保存される状態と終了時の扱い

メモリの `active_room_states` が現在の状態で、通常保存は約2秒後にDBへ集約する。起動時にルーム一覧を読み、各ルームの状態は `get_room_state()` の初回参照でDBから読み込む。ルーム所有者・メンバー権限・長期ログはルームJSONとは別のテーブルにもある。

保存の失敗時は1回再試行し、それでも失敗すれば未保存としてメモリに保持する。自動再試行はそこで止め、次の保存要求・明示フラッシュ・正常終了で再試行する。正常終了では最大2回の保存を試し、残る未保存件数をERRORで記録する。終了時の保存も失敗した内容は再起動で復元できない。保存要求の受付成功はDBへのコミット成功を意味しない。

`os._exit()`、プロセスの強制終了、電源断ではatexitが走る保証がなく、最後のDBコミット以降の状態が失われる。通常の約2秒は保存要求から初回試行までの待ちであり、DB障害・処理待ちを含む未保存時間の上限ではない。

## 隔離環境での検証

自動検証は `tests/test_persistence_recovery.py` と `tests/test_persistence_process_recovery.py`。前者は一時DBと制御した保存タイミングで失敗経路を検証し、後者は別プロセスで実DB保存・終了・復元・SQLiteバックアップを確認する。ネットワークや本番データを使用しない。

```powershell
python -m pytest -q tests/test_persistence_recovery.py tests/test_persistence_process_recovery.py tests/test_room_log_archive.py tests/test_sqlite_runtime_config.py
```

本番接続の環境変数を持ち込まず、テスト用SQLite URLを明示する。自動検証が作るDBとバックアップはpytestの一時ディレクトリ内に置き、Gitへ追加しない。現役DBをコピーして試験データとして使わない。

2026-10-31の確認結果:

| 条件 | 結果 |
|---|---|
| 通常のデバウンス保存 | 連続する保存要求から最新のHP・座標・宣言・ログを別プロセスで復元 |
| 保存待ち中の正常終了 | 実際のatexit保存から最新状態を復元 |
| 終了時の一時失敗・通常再試行枠の枯渇・初回即時保存の失敗 | 終了時の試行で回復後の最新状態を保存し、別プロセスで復元 |
| 継続する保存失敗 | 未保存がメモリに残り、自動再スケジュールが止まる。即時保存はFalse、終了時は未保存をERRORで記録 |
| 保存中の正常終了 | 進行中のコミットを待って終了処理が完了 |
| 強制終了 | 最後のコミット済み状態を復元。保存待ちだった最新変更は含まれない |
| WALを含むSQLiteのバックアップ・別DBへの復元 | ルーム状態、所有者、ユーザー、メンバー権限、長期ログが一致 |

全件検証は1399 passed / 2 skipped（172.34秒）。同じプロセスで検証終了時の保存待ちが空であることも確認した。

## バックアップと復元の範囲

SQLiteを稼働中に扱う場合、DB本体だけのファイルコピーではWALにあるコミットを取りこぼしうる。隔離検証ではPython sqlite3の `Connection.backup()` で一貫したコピーを作り、そのコピーから別DBへ戻して内容を確認する。

このDB検証にはCloudinary上の画像実体、Google Sheets、ソース・静的ファイルは含まれない。DBの復元だけで外部素材や別サービスまで復旧したとは扱わない。ローカルDBの内容を本番へ移す処理も含めない。

## 本番で残る確認

2026-10-31のユーザー回答では、DBプラン・バックアップ設定は「不明」。Renderの接続ツールは利用できず、画面全体の取得は自動承認レビューで拒否された。その後のChrome操作も、URLを確定できないというツール側の安全確認で停止したため、ユーザー提供のスクリーンショットで確認している。契約・バックアップ設定・復元操作の変更は行っていない。

確認先の訂正: [既存の導入手順](account_system_deploy_runbook.md)には「本番DBはNeon」と明記されていた。今回のRender一覧にもアプリ1件だけが表示され、DBサービスは見当たらない。アプリはRender Free・Singaporeと確認した。ローカル `.env` に `DATABASE_URL` はなく、Renderの実接続先との最終照合は残る。以後はユーザー提示のNeon画面で確認する。

上記は設定表示の確認であり、復元操作の成功実績ではない。履歴復元の表示とスナップショット作成は分けて記録する。Configure・Create・Restore・Upgrade等の操作は行っていない。

残る確認:

- 過去6時間より前の状態を残す必要性と、追加バックアップの保管方法・頻度・運用負担。
- 実際に参照できる復元履歴の期間、契約・設定を変更する場合の上限と費用。
- 本番バックアップからの非本番DB復元と、Linux/eventlet/Gunicornの正常終了・時間切れ時の保存。非本番PostgreSQLの取得・別DB復元は2026-11-01に検証済み。
- 接続障害が終了猶予を超えた場合の未保存範囲。
- ユーザーが許容する未保存時間と復旧時間、保存失敗の通知方針。

本番の復元・契約変更はこの手順の作成だけで実行しない。仕様は[F01 Part 7](../implemented/F01_Operations_Manual.md)、進捗と検証結果は[課題一覧](../projects/app_foundation/backlog.md)を参照。

## 次の優先順位の決定

画面確認でアプリ・DBとも無料プランと分かり、Neonの履歴復元は過去6時間、スナップショットは0件・定期作成未設定と確認した。2026-11-01のユーザー指示「お薦めの順番でやって」に基づき、次の順序で進める。

1. 追加の有料契約を使わず、セッション後・更新前にPCへ手動でバックアップを保管する運用を整える。
2. 運用の手間を減らすため、バックアップ自動化と必要に応じた少額課金の案を比較する。
3. 当面は現在の履歴復元設定を維持し、速度の計測を先に進める。

まず1の実装と非本番検証を進める。実施手順の正本は[PostgreSQL手元バックアップ](postgres_backup_runbook.md)。新しい有料契約・定期ジョブ・既存バックアップの自動削除・本番への復元はこの指示では行わない。接続URLはチャットやGitへ転記せず、実行時にPC上で入力する。
