# ジェムリアTRPG マスターデータベース・プロジェクト

作成日: 2026-11-04
形態: 常設。段階ごとの計画に完了を設け、プロジェクト自体は継続する。

## 目的

ジェムリアTRPGのデータを、アプリの中の1つのデータベースとしてまとめて作り・確かめ・探せるようにする。対象は、スキル・バフ/デバフ・パッシブ・用語などのルールの部品と、敵キャラ・行動パターン・編成・ステージなどのシナリオの資産。

着手時は、ルールの部品が Google Sheets、シナリオの資産がアプリの DBと、置き場も作り方も分かれている。これを共通の土台の上に揃え、新しいスキルや敵を作る手間を下げ、サーバーのメンバーも権限の範囲で作成に加われるようにする。

## 2つの層と共通の土台

| 層 | 中身 | 性格 | 今の置き場 |
|---|---|---|---|
| ルールの部品 | スキル・バフ/デバフ・パッシブ・用語・アイテム・輝化スキル・召喚テンプレート | ゲーム全体で1つ。制作者が下書きを作り、アプリ管理者が承認して公開する | Google Sheets → JSON キャッシュ |
| シナリオの資産 | 敵キャラ・行動パターン・編成・ステージ・コレクション | 作った人が持ち、ACL で共有する | DB の `preset_resources`（D01 Part 4・6） |

2つの層は、次の共通の土台に乗せる。

- **種類＋ID で持つ**：種類・安定した ID・中身の JSON・版（`revision`）で持つ。表は流れの違いで分ける。シナリオの資産は持ち主が直接保存する `preset_resources`、ルールの部品は承認して公開する `catalog_entries`・`catalog_drafts`・`catalog_history`（計画60 論点10）。
- **参照のつながり**：敵がどのスキル・パッシブを使うか、あるバフがどこで使われているかを引ける。参照先の廃止や削除の影響を、保存の前に見せる。つながりは表に保存せず、必要なときに中身の JSON から計算する。両方の層で共通の関数を使う。
- **履歴**：誰がいつ何を変えたかを残し、前の版に戻せる。
- **検査**：効果タイプのスキーマ（`manager/battle/effect_handlers/` の `SCHEMAS`、B01「効果タイプの追加手順」・C01 §17）で、保存の前に JSON を確かめる。
- **横断の検索と閲覧**：種類をまたいで探し、データ同士のつながりをたどれる画面。これがデータベースの顔になる。

## 段階1の決まり（計画60から移した。2026-11-04〜14 ユーザー決定）

実装の細部は各仕様書にある。ここには、仕様書に書きにくい方針と、その根拠の要点だけを残す（決定の全文は計画60を削除する前のコミット bbd6428 の `manuals/planned/60_Master_Data_Studio_Plan.md`にある）。

- **正本**：ルールの部品7種類（用語・バフ・スキル・アイテム・特殊パッシブ・輝化スキル・召喚テンプレート）は DB の `catalog_entries`・`catalog_drafts`・`catalog_history` が正本。Google Sheets は読まない。DB が空のときだけ `data/cache/` から最初の中身を入れる。手元へは `python app.py --pull` で本番の公開データを取る（F01）。検査と承認を必ず通る入口を1つにし、push なしで反映するため。
- **権限**：閲覧は全員、下書きと申請はアプリ管理者が指名した制作者（`is_catalog_author`）、承認はアプリ管理者（F01 Part 1-B）。AI エージェントに下書きを作らせるときは、ユーザーの権限で制作者として API を使う。
- **ID**：下書きは仮の ID（`X-` で始まる）で作り、承認のときに承認者が正式な ID を付け、仮の ID を参照するほかの下書きも書き換える。スキルの正式な ID はカテゴリ（Ps・Pb・Pp・Ms・Mb・Mp・D・B・C・E）の頭で番号を取る。公開した後は ID を変えず、消す代わりに「廃止」にする（新しく選ぶ一覧からは外し、使っている所ではそのまま動く）。ID はチャットパレット・持ちキャラなど、アプリが把握しきれない所からも参照されるため。
- **検査の段階**：下書きの保存は参照の問題（参照先が無い・廃止・仮の ID）で止めず、画面に一覧を出す。申請・承認では形・参照先が無い・仮の ID で止め、廃止は注意だけ出して承認者が判断する。
- **ネタバレ**：下書きは制作者とアプリ管理者だけが見る。公開したデータは全員が見られる（マスターデータの公開 API は認証なし）。図鑑では出会い・knownで未解禁の敵専用データの表示を伏せる（計画66）。公開APIやルームへの配信内容はそのままにする。
- **公開の反映**：承認したらすぐ全体に反映する（共有の辞書を入れ替え、`catalog_updated` で画面に裏で読み直させる）。ルームのログや画面の知らせは出さない。戦闘中のルームも、次にそのデータを使った時点から新しい定義になる。
- **文章と JSON**：アプリに LLM は入れない。決まった言い回しの読み取り（文章から作る）と、効果から文章を作る機能をアプリに持ち、自由な文章からの作成は外の AI エージェントが API で下書きを作る。費用と API キーをアプリに持ち込まないため。
- **試し撃ち**：管理画面はスキルの素の性能（威力の見込み）まで。本物の処理で1回ぶつける機能と勝率は計画63（戦闘マスター）へ移した。短い戦闘を何回も回す集計は CLI（F03）をローカルで使う。
- **未対応の効果のリクエスト**：管理画面の中の一覧に置き、元の下書きにひもづける。知らせは作らず、件数と一覧で分かるようにする（E02・F01）。
- **未決定：一括編集の手段**。表計算でしていた一括の書き換え・見比べを何で補うか（CSV の書き出し・読み込み、管理画面の軽い表計算、AI エージェントが API で下書きをまとめて作る、など）。分類と印の付け外しはPR66-5で実装済み。それ以外の一括編集は、必要になった段階で決める。
