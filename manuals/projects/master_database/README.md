# ジェムリアTRPG マスターデータベース・プロジェクト

作成日: 2026-11-04
形態: 常設。段階ごとの計画に完了を設け、プロジェクト自体は継続する。

## 目的

ジェムリアTRPGのデータを、アプリの中の1つのデータベースとしてまとめて作り・確かめ・探せるようにする。対象は、スキル・バフ/デバフ・パッシブ・用語などのルールの部品と、敵キャラ・行動パターン・編成・ステージなどのシナリオの資産。

今は、ルールの部品が Google Sheets、シナリオの資産がアプリの DB（戦闘専用プリセット）と、置き場も作り方も分かれている。これを共通の土台の上に揃え、新しいスキルや敵を作る手間を下げ、サーバーのメンバーも権限の範囲で作成に加われるようにする。

## 2つの層と共通の土台

| 層 | 中身 | 性格 | 今の置き場 |
|---|---|---|---|
| ルールの部品 | スキル・バフ/デバフ・パッシブ・用語・アイテム・輝化スキル・召喚テンプレート | ゲーム全体で1つ。制作者が下書きを作り、アプリ管理者が承認して公開する | Google Sheets → JSON キャッシュ |
| シナリオの資産 | 敵キャラ・行動パターン・編成・ステージ・コレクション | 作った人が持ち、ACL で共有する | DB の `preset_resources`（D01 Part 4・6） |

2つの層は、次の共通の土台に乗せる。

- **種類＋ID で持つ**：種類・安定した ID・中身の JSON・版（`revision`）で持つ。表は流れの違いで分ける。シナリオの資産は持ち主が直接保存する `preset_resources`、ルールの部品は承認して公開する `catalog_entries`・`catalog_drafts`・`catalog_history`（計画60 論点10）。
- **参照のつながり**：敵がどのスキル・パッシブを使うか、あるバフがどこで使われているかを引ける。参照先の廃止や削除の影響を、保存の前に見せる。つながりは表に保存せず、必要なときに中身の JSON から計算する。両方の層で共通の関数を使う。
- **履歴**：誰がいつ何を変えたかを残し、前の版に戻せる。
- **検査**：効果タイプのスキーマ（計画60 §3.1）で、保存の前に JSON を確かめる。
- **横断の検索と閲覧**：種類をまたいで探し、データ同士のつながりをたどれる画面。これがデータベースの顔になる。

## 方針

1. 段階ごとに、それだけで役に立つ単位で出す。最終形を一度に作らない。
2. 新しい保存の仕組みを種類ごとに作らない。共通の土台（種類＋ID＋中身＋版）に揃える。
3. 後方互換やデータ移行は行わず、理想の形に作り直す（[AGENTS.md](../../../AGENTS.md)）。
4. 資料、テスト、最小実装、不要コード・資料の確認の順で進める。
