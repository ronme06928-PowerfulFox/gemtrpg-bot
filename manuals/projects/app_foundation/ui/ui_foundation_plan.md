# アプリ全体のUI計画（見た目と操作の共通の決まり）

作成日: 2026-11-15
状態: 見た目の元を決定（2026-11-15）。ひな形 `ui_template.html` の「紙と金・控えめ」を元にする。次は §7.2 の管理の側の試作を、ひな形の部品で作る。ルーム内の配置は §7.3（計画61 PR61-4 のとき）。

## 1. 目的と位置づけ

管理画面（マスターデータ・ユニット管理）、ロビー、ルームの画面で、文言・大きさ・操作の置き場・色・飾りがばらばらにならないよう、アプリ全体の共通の決まりを持つ。新しい画面を作るときは、この決まりを先に当て、画面ごとの計画では差分だけを決める。

文書の役割：

| 文書 | 役割 |
|---|---|
| この計画 | アプリ全体の共通の決まり（案と決定）。画面をまたぐ判断の正本 |
| `manuals/ui_design_decision_log.md` | 画面ごとに、実装した見た目と理由の記録 |
| `manuals/implemented/E01`・`E02` | 実装済みの UI の仕様 |
| `ui_template.html`（この計画と同じフォルダ） | 見た目の元になるひな形。トークン・部品・画面のひな形を1ページに置き、テーマと飾りの濃さを切り替えられる |
| `static/css/modules/common_ui.css` | 共通の色・角丸などのトークンの実装 |
| 各機能の計画（計画57・60・61 など） | その画面だけの見た目（戦闘の演出の秒数・SE などは機能の計画が正） |

対象としないもの：モバイル版（開発停止中）、戦闘の演出の秒数・SE（計画52・55・57）、本（PDF）の組版（計画46、`typst_manual/`）。本の色は、色の元として参照する。

## 2. 今ある決まりと出典

各項目に次の印を付ける。

- **［共通］** アプリ全体の原則。新しい画面にもそのまま当てる。
- **［画面別］** ある画面で決めた取り決め。ほかの画面へ広げるかは §6 で決める。
- **［見直し］** 今の画面どうしでぶつかっていて、今回見直す点（§6 で扱う）。

### 2.1 文言

- ［共通］和語の言い回しを減らし、熟語・カタカナ語で短く書く（例：「使っている編成」→「使用中の編成」、「保存の前の検査」→「保存前チェック」、「JSON から取り込む」→「JSONインポート」）。出典：計画61 §3.7（2026-11-14 ユーザーの指摘）。
- ［共通］注意書きを増やさず、構造（並べ方・見出し・札）で意味を伝える。補足は短い ⓘ の説明にする。出典：計画60 §5.15、旧 §6-3（コミット 6c4526bb）。
- ［共通］内部のキー（`state_name`・`type` 名など）は、ふだんは画面に出さない。例外として、マスターデータの効果の編集には「効果タイプの英字のキーも出す」チェックがあり、押したときだけキーを並べて出す（`static/js/master_data/skill_effects.js`）。出典：計画60 §5.15、旧 §6-3。
- ［共通］変更できない正式な ID は、入力欄にせず文字で見せる。出典：計画60。
- ［画面別］言葉の使い分け：一覧から取り除くのは「外す」、データそのものを消すのは「削除」、選んでいる物を空にするのは「解除」。出典：計画61 §3.10。ほかの画面へ広げる候補。

### 2.2 大きさと空白（管理画面）

- ［画面別］ユニット管理の密な一覧から決めた値：文字は13px ほど、見出しだけ少し大きく強弱で区切る。すき間は4〜8px、枠の内側は8〜10px。1件を1〜2行の行で見せ、長い文は1行で切って、開いたときだけ全文を出す。出典：計画61 §3.9（論点25）。
- ［画面別］入力欄は中身に合った幅（数値は数文字分、名前は1行分）。ただしステージの説明欄のような長い文の欄は全幅にする。出典：計画61 §3.9。
- ［見直し］マスターデータの画面（`master_data.css`）はこれより大きい。13px をほかの管理画面にも当てるかは、件数だけでなく §6-2 の基準で比べて決める。

### 2.3 読み物のページ（使い方ページなど）

- ［画面別］使い方ページ（`static/help/master_data.html`）：本文は16px・行間1.85・1行約38字。目次は幅900px以上で左に固定し、それより狭いときは固定しない。図は手順の下、写真は要る所を切り出す。出典：計画60 §5.20。
- ［共通］本文の行の高さは文字の150%以上にする（DADS）。利用者が行間・字間などを上書きしても内容と操作を失わないようにする（WCAG 1.4.12。ページの既定値の決まりではなく、上書きされても崩れないことの決まり）。

### 2.4 操作の置き場と大事さ

- ［画面別］ユニット管理の置き場の段（計画61 §3.10、論点27）：
  1. 画面全体の操作：見出しの右（書き出し・取り込み、再読み込み、閉じる）。
  2. 一覧の操作：一覧の見出しの右に「＋ 新規」。検索と絞り込みはその下。
  3. 開いている1件の操作：下の帯。右に「保存」と「変更を破棄」、左に「その他 ▾」（廃止・削除などをしまう）。戻るは左上。
  4. 節の操作：節の見出しの右に、対象名の付いた「＋ 〇〇を追加」。見出しごと上に留める。
  5. 1行の操作：行の右端に文字で。外す・削除は一番右に離す。
  6. 窓：見出しの右に「閉じる」、主の操作は窓の下の右に1つ。
- ［共通］大事さは3段：主（塗りつぶし）、ふつう（枠だけ）、危険（赤い文字）。出典：計画60 §5.14（決まり4・5）、計画61 §3.10。
- ［見直し］「主は1つの面に1つまで」は、今の画面とぶつかる所がある。
  - マスターの編集：主は「承認を申請」、「下書きを保存」は副（`static/js/master_data/workspace.js`）。
  - マスターの却下の確定は、赤い塗りつぶし。
  - 配置の画面：各行の「追加」も主ボタンの色（`static/js/modals/preset_deployment_browser.js`）。
  - 何を主にするか、どこまでを1つの場面と数えるか、危険な確定（却下・削除の確定）をどう見せるかを §6-4 で決める。
- ［画面別］候補から選ぶ：標準の選択欄（プルダウン）の候補が左上から開いてずれる場合の対策として、候補をページの中の一覧で選ぶ。出典：計画61 §3.7・§3.10。
- ［画面別］続けて追加する候補の窓：追加しても閉じず、検索・分類・一覧のスクロール位置を保ち、追加した物は「追加済み」と示す。編成のメンバーは同じユニットを何度でも追加でき、回数と今の枠数を示す。出典：計画61 §3.10。

### 2.5 確認・未保存・知らせ

- ［共通］下書き・保存は、保存したときに作る。保存していない変更があるまま離れようとしたら確かめる。「未保存」を出し、「変更を破棄」は未保存のときだけ押せる。出典：計画60 §5.14（決まり8）、計画61 §3.10。マスターデータでは、下書きの初回作成の入口は「下書きを保存」と「承認を申請」の両方。
- ［共通］共通の確認窓（出典：E02 Part 16、計画61 PR61-2c、`static/js/main.js`）：
  - Enter は印の付いたボタンだけを動かす。最初の印は呼び出しごとに選び、削除・破棄・取り下げなど危険な確認は「キャンセル側」。
  - 入力欄のある確認は、入力欄での Enter で確定する。
  - Escape と背景のクリックはキャンセル。
  - 閉じたあと、開く前の場所にフォーカスを戻す。
- ［共通］操作の直後にその場で手応えを返し、待ちはその場所に出す。出典：計画60。
- ［共通］選んだ値に応じて、要る欄だけを出す。出典：計画60。
- ［共通］知らせ：成功は右下に浮かべて数秒で消し、画面をずらさない。誤りは消えず、閉じるボタンを付ける。出典：計画60 §5.14（決まり9）。
- ［共通］浮かぶ枠（候補など）は、枠とその開くボタン以外のどこを押しても閉じ、押した先にはそのままクリックを通す。Escape でも閉じる。出典：計画60 §5.14（決まり9）。

### 2.6 色と札

- ［共通］コントラスト：文字は背景に対して4.5:1以上、操作の枠（入力欄・ボタンなど）は3:1以上。飾りの線（カード・区切り）は薄い色でよい（`--cat-edge` と `--cat-control` を分けた）。出典：計画60 §5.14（決まり3）・§5.15。
- ［共通］色だけに頼らない：状態・陣営・公開範囲・警告は、文字・枠・形も併用する（廃止と編集中は破線の枠など）。出典：計画60 §5.14（決まり2）、`ui_design_decision_log.md` §4、計画61 §3.9。
- ［共通］危険は赤、注意は黄土。出典：`ui_design_decision_log.md` §4。

- ［共通］管理画面とルームは PC の Web が中心（モバイル版は開発停止）。1280px で確かめる。
- ［画面別］管理画面（計画60・61）：680px では列を縦に積み、下の帯は画面の下に留める。出典：計画60 §5.14（決まり5）、計画61。

- ［見直し］上の画面別のやり方のうち、どれを共通の部品にするかは、§6-1 の画面構造と一緒に決める。

## 4. 共通の決まり（案）

§2 の［共通］を前提に、色と飾りをそろえる案。値はレビューで計算したコントラスト比（白地は `#fff`）を添える。

**見た目の元（2026-11-15 決定）**：白い地をやめ、ファンタジーの雰囲気を重く見る。ひな形 `ui_template.html` の「紙と金・控えめ」を、管理画面・メインメニュー・読み物の元にする。

- 地は紙の色（面 `#f7efdd`・淡い面 `#efe3c8`・ページ `#dccaa2`）、文字はセピア（本文 `#2d2618`・補助 `#6b5c45`）。主はサファイアの青 `#1f4fa3` に金の縁。値の正本はひな形の `[data-theme="paper"]`。
- 飾りは「控えめ」：紙の質感（淡いグラデーションと細かいノイズ）、明朝体の見出し、金の細い線、ボタンの光沢、カットの入った宝石の印。額縁・飾り罫・輝き・動きの「濃いめ」は使わない。
- 枠・見出し・ボタンを飾り、一覧の行と本文はゴシック体のまま静かにする。
- ルームと戦闘は「夜色と金」（濃紺の地、主は金。ひな形の `[data-theme="night"]`）を案とする。目での確認はこれから。
- どのテーマも、ひな形の実測でコントラストの基準（§2.6）を満たす。新しい部品は、先にひな形に足してから画面に当てる。

以下の1〜6は、この元の上での決まり。

1. **色のトークンを1つの系統にまとめる**：`common_ui.css` に意味の名前（文字・補助の文字・飾りの線・操作の枠・面・主・危険・注意・追加・味方・敵）でトークンを置き、`--cat-*`・`--bo-*` はそれを使う。名前は共有し、明るい画面と暗い画面、用途ごとに値を持つ。
   - 本の灰青 `#647080` は白で5.03:1で補助の文字に使えるが、暗い地 `#222` では3.16:1で足りない。暗い画面には別の値を持つ。
   - 操作の枠 `#7b8798` は白で3.65:1、`#f5f7fa` で3.40:1で使える。
   - 金・水色の塗りを白地の境界に使うと2.29:1・2.06:1で足りないので、枠の線を足す。
2. **分類の色に宝石の色を使う**：種類のタブ（ユニット・編成・ステージ）、スキルの10分類（Ps・Pb・Pp・Ms・Mb・Mp・B・C・D・E）、マスターデータの7種類に宝石の色を割り当て、本と見た目をつなぐ。
   - 使うのは小さな印（タブ・行の左端・札）と淡い面まで。濃い色と淡い色の組をそのまま文字と背景にすると、ダイヤ3.24:1・トパーズ3.82:1・シトリン3.88:1で足りないので、文字は本文の色にする。
   - 淡い面だけでは選んでいる印として弱いので、下線や選択の印も付ける。
3. **スキルの札は戦闘と同じ色**：宣言パネルの10組と既定色は5.45〜10.31:1で、そのまま共通のクラスに移せる。
4. **陣営は赤と青**：配置のときのキャラの青は白で3.98:1、赤は淡い赤の地で3.96:1で、札の文字には足りない。管理画面の札には、配置の画面の味方5.81:1・敵6.26:1の組（`preset_deployment.css`）を使う。「敵」と「危険・削除」は同じ赤系でも別の用途として別のトークンにする。
5. **飾りは「控えめ」の範囲**：紙の質感、明朝体の見出し、金の細い線、ボタンの光沢、宝石の印と淡い面まで。額縁・大きな絵・動く光は使わない。影は、常に出ている面（薄い影）と、候補・知らせ・窓など重なる物（濃い影）とで別のトークンにする。
6. **大事さの3段に色を合わせる**：主は主の色の塗りつぶし、ふつうは操作の枠の色の枠だけ、危険は赤い文字。何を主にするか・危険な確定の見せ方は §6-4 で決めてから当てる。

## 6. 未決定事項

先に決めるのは §7.1 の「試す場面と評価基準」まで。1〜4 は試作を見てから決める。

1. **画面の組み立て**（独立した論点）：
   - ① ロビーから管理の専用ページへ進む。
   - ② 共通のメニューから、全幅の作業の領域を切り替える。
   - ③ ルームを見ながら、配置の候補や履歴を横のペインで開く。
   - ①〜③は併用できる。今の見込みは、長い編集・差分の承認は①か②、フィールドを見ながらの配置は③、短い確認は窓（モーダル）。
   - URL を持つ範囲（どの画面にブラウザーの「戻る」で戻れるか）は、戻ったときに一覧・スクロール位置・未保存の入力が保てるかと、今の入退室・GM の権限・Socket の再接続（`static/js/main.js`）を調べてから決める。
   - **決定（2026-11-15）**：ユニット管理とマスターデータは、将来のメインメニュー（計画62の候補）から開く専用の画面にする。ルーム内のユニットの配置は、ユニット管理で作ったユニット・編成・ステージを使う、ルーム専用の UI にする。配置で横のペインを採るかは、§7.2 の試作の操作を見て決める。
2. **文字の密度**：13px（ユニット管理）と16px（使い方ページ）のどちらへ寄せるか。件数だけでなく、長い日本語の名前を見比べやすいか、押し間違えないか、200%に拡大しても使えるか、上下に留めた帯がフォーカスを隠さないか（WCAG 2.4.11）で比べる。
3. **色の意味**：宝石の色の割り当ては**分類別に決定**（2026-11-15。分類ごとに違う宝石を当て、見分けやすさを優先する。本の章の割り当てとは別）。今の割り当ては次のとおりで、画面に当てるときに調整してよい。
   - ユニット管理：ユニット＝エメラルド、編成＝サファイア、ステージ＝ルビー。
   - マスターデータ：用語＝水晶、バフ＝エメラルド、スキル＝サファイア、アイテム＝トパーズ、特殊パッシブ＝アメジスト、輝化スキル＝シトリン、召喚テンプレート＝ルビー。
   - スキルの分類：Ps＝ルビー、Pb＝トパーズ、Pp＝シトリン、Ms＝サファイア、Mb＝アメジスト、Mp＝エメラルド、B＝水晶、C＝ダイヤモンド、D＝オニキス、E＝サファイア。
   - メインメニュー：セッション＝サファイア、ダンジョン＝ルビー、マイキャラクター＝トパーズ、使い方＝水晶、ユニット管理＝エメラルド、マスターデータ＝アメジスト。
   - 残り：分類・陣営・警告・選択を同じ行に出したときに区別できるかを、ふつう・ホバー・フォーカスのときで測る。
4. **操作の状態と大事さ**：何を主にするか、どこまでを1つの場面と数えるか、危険な確定（却下・削除）を赤い塗りつぶしにするか赤い文字にするか（§2.4［見直し］）。
5. **トークンの置き場と名前**：`common_ui.css` に寄せるか、新しいファイルにするか。意味の名前の付け方、明暗の値の持ち方。
6. **飾りの範囲**：濃さは「控えめ」に決定（§4）。残りは、宝石の印をどこまで使うか（見出し・タブ・空の状態の表示など）と、ルーム・戦闘の「夜色と金」の確認。
7. **戦闘の画面への適用**：トークンを戦闘の画面にも使うか。戦闘の操作の組み立ては配色と別に判断する。
8. **記録の置き場**：画面ごとの記録は `ui_design_decision_log.md` に続けて書くか（今は 2026-08 の2件で止まっている）。

## 7. 段階（案）

1. 試す場面と評価基準を決める（§7.1）。
2. 画面の組み立ての試作（§7.1 の3つの場面を①〜③の案で通す）を作り、見比べる。
3. 試作を見て、画面の組み立てと部品の役割（§6-1・6-4）、文字の密度（§6-2）、色の意味（§6-3）を決める。1回目の試作（`scripts/ui_layout_proto/`）で画面の分け方を決めた（§6-1）。次は §7.2 の試作で、管理の側の形と色付けを決める。ルーム内の配置は §7.3。
4. 今の色を保ったまま、トークンを1つの系統にまとめる（見た目を変えない置き換え）。
5. ユニット管理に当てる。
6. マスターデータに当て、使い方ページの写真を撮り直す。
7. ロビーと配置の画面に当てる。

戦闘の操作の組み立ては、配色の移行と別に判断する。仕様（E02）と `ui_design_decision_log.md` は、段階ごとに直す。

### 7.1 試す場面と評価基準（案）

- 場面：
  1. ユニットの編集（計画61）
  2. マスターデータの差分の承認（計画60）
  3. ルームでの配置（配置の画面）
- 通す流れ：管理は「一覧 → 編集 → 一覧に戻る」、ゲームは「盤面 → 配置の候補 → 確定 → 盤面に戻る」を、それぞれの案で通す。
- 比べること：
  - 盤面の見通し（ルームの中で開いたとき、盤面がどれだけ見えるか）
  - 操作の迷い（次に押す所がすぐ分かるか、戻り方が分かるか）
  - ウィンドウの周りの余白（広い画面で間延びしないか、狭い画面で詰まらないか）
  - ジェムリアらしい楽しさ（色付けと飾り）
  - 戻ったときに、一覧・スクロール位置・未保存の入力が保てるか

### 7.2 2回目の試作（管理の側：メインメニュー・管理画面・色付け）

画面の分け方が決まり（§6-1）、管理の側は素材と色の案（§4）がそろっているので、先に管理の側を試す。

- 見た目は、ひな形 `ui_template.html` の「紙と金・控えめ」のトークンと部品を使う。
- 通す流れ：メインメニュー → ユニット管理（一覧 → 編集 → 一覧に戻る）→ メインメニュー → マスターデータ（承認待ち → 差分 → 承認 → 次の案件）→ メインメニュー → ルームの一覧（ロビー）。
- 2026-11-15：`scripts/ui_layout_proto/` の試作を「紙と金・控えめ」で作り直した。メインメニューは、遊ぶ入口（セッション・ダンジョン）を上、マイキャラクターと使い方を中、データ管理を下、アカウントを右上に置く。試作の中のユニット管理・マスターデータの画面は、行き来を確かめるための仮の画面で、本番の画面の形ではない。本番の画面には、段階5・6でトークンと部品を当てる。
- 見比べること：
  - メインメニューの形（何を並べるか、制作者・GM・一般で何が変わるか）。
  - ユニット管理とマスターデータを専用の画面にしたときの見え方。文字の密度（§6-2）は13pxと16pxを切り替えて比べる。
  - 宝石の色の割り当て（どの分類にどの宝石を当てるか）を2案ほど切り替えて比べる。
- 比べることは §7.1 の「操作の迷い・周りの余白・ジェムリアらしい楽しさ・戻ったときに保てるか」。

### 7.3 ルーム内の配置（計画61 PR61-4 のときに試作する）

配置は計画61 の PR61-4（ルームからの配置）で作り直す画面なので、下の「決めてほしい点」が決まってから試作する。2026-11-15 に、操作ガイド（06・07・04）、D01 Part 2・4・5、計画61、`preset_deployment_browser.js`・`manager/preset_deployment.py` を照らし合わせて整理した。

**今の流れ（通常ルーム）**：GM が「プリセット配置」を開き、ステージ・編成・キャラクターを選ぶ。プレビューは件数だけ（新規・置換で外す数・ステージの要素）。確定すると窓が閉じ、新しいキャラは空いている座標へ自動で置かれる。位置は盤面で直し、「戦闘突入」へ進む。終結後は通常のキャラの HP・MP・FP と配置が残り、倒した敵も盤面に残るので、次の遭遇では敵編成の置換で入れ替える。戦闘専用ルームでは、置く先が下書きで、確定のあとに「戦闘突入を確認」か「詳細調整」へ進む。

**気になる点（資料と実装の食い違い・挙動）**：

- 計画61 の論点22・PR61-4（ルームの中からユニット管理を開き、ルームへ配置）が、§6-1 の決定（配置はルーム専用の UI）と食い違う。計画61 を直す。
- 操作ガイド06 は「通常プリセット」、画面の見出しは「プリセット配置」。
- 配置を確定した時点で、敵が全員の盤面と探索画面に出る（探索画面は盤面に置かれたキャラを立ち絵として全部出す）。「準備」と「登場」が分かれていない。
- 計画61 は `gmOnly` を「GM限定表示」と呼ぶが、実際は「GMのみ操作可能」の印。駒を PL から隠す手段はない。
- 味方編成を置換にすると、PC を含めて味方が全員外れる（`_remove_side`）。
- ステージのフィールド効果は、今の効果に足さず丸ごと差し替える。
- 戦闘開始時の効果は、戦闘突入ではなく配置のときに処理する（`_initialize_battle_start`）。突入のときの扱いは未確認。
- 空いている座標が足りないと未配置（-1,-1）になるが、プレビューに出ない。
- 戦闘中の配置はサーバーが止めていないので増援はできるが、ラウンドの途中で足したキャラがいつ行動に入るかは仕様にない。

**画面の案**：

- 入口は目的から始め、素材の種類は中の絞り込みにする。「遭遇を準備」（既定は敵を置換、ステージの要素を入れ替え、単体も足せる）、「増援・NPC を追加」（既定は追加、戦闘中も開ける）、戦闘専用ルームでは「下書きを組む」（確認は人数・担当・ready）。
- 盤面が要るのは選んでいる間ではなく確認のとき。選ぶときは広い一覧、確認では盤面に仮置きの駒を重ね、横のペインに「維持・除外・追加」の数と名前を出す。確定したら盤面に戻り、置いた駒を目立たせて「戦闘突入」への近道を出す。
- 準備と登場を分ける案：「遭遇を準備」の確定はルームの準備中の遭遇にとどめ、「登場」で盤面に出す。戦闘専用ルームの下書きと同じ形にそろえられる（仕様の変更）。

**試作の場面**：

- A：探索中の通常ルーム。PC4人は HP が減り、前の敵2体が残る。「遭遇を準備」でステージ（背景・効果・敵5体）を当て、確認で「維持4・除外2・追加5」と仮置きを見て、1体の位置を直して確定し、盤面から戦闘突入する。
- B：戦闘中のラウンド2の終わりに、増援を1体足す。置き場所を確かめて確定し、盤面に戻る。
- C：戦闘専用ルームの下書き。ステージを当てると味方が足りず、問題点を見て詳細調整へ進む。
- D（比較）：A と同じ流れを、素材の種類から探す入口（今のタブ）で通す。
- 比べること：盤面がいつ必要だったか、置換か追加かで迷ったか、PL に見えるのはいつか。

**決めてほしい点**：準備と登場を分けるか。実際の卓での頻度（遭遇を事前に組むかその場で選ぶか、1回の卓の遭遇の数、増援の多さ、準備中の敵を PL に見せたくない場面があるか）。
