# アプリ基盤・安定運用プロジェクト

作成日: 2026-10-31
形態: 常設。個別の改善に完了を設け、プロジェクト自体は継続する。

## 目的

GemDiceBotで、待ち時間や切断に進行を妨げられず、安心してセッションを続けられる土台を育てる。通信・計算・描画、データ保存と復旧、運用費用、リポジトリ構成を一つの継続的な改善活動として扱う。

無料でできる改善を優先し、少額課金は効果と維持の手間を比べて選ぶ。ファイルや機能が増えても、次の開発者・AIが所在と責務を追える構成を保つ。

## 対象範囲

- 操作受付から結果が見えるまでの応答、通信量、サーバーとブラウザの負荷。
- 状態の整合性、保存、切断・再接続、再起動・デプロイからの復旧。
- Render、DB、Cloudinaryなどの配置・利用量・費用と、代替構成の比較。
- フォルダ、モジュール、スクリプト、資料、テスト、生成物、ローカル出力の整理。
- 繰り返し実施できる計測・検証と、必要最小限の運用手順。

戦闘ルール・バランスや、演出の秒数・SE・文字サイズ・配色は、それぞれの機能計画を正とする。応答計測と画面負荷は、計画58（2026-11-02に完了・削除）から引き取り、このプロジェクトの `PERF-BASELINE` が担当する。機能計画と同じ計測や変更を重ねて実施せず、担当文書と結果へのリンクを課題一覧に残す。

## 改善の原則

1. 体感の報告、コードで確認した事実、計測結果、仮説を区別する。
2. まず計測し、効果の見込める小さい変更から進める。フォルダ移動だけで実行速度が上がるとは扱わない。
3. 個人用アプリに合うKISSな構成を選ぶ。Redis、タスクキュー、サービス分割などは必要性を確認してから検討する。
4. 状態の正、権限検証、順序、重複操作への対処を保つ。速くするために整合性を省かない。
5. 資料、テスト、最小実装、不要コード・資料の確認の順で進める。詳細な規則は[AGENTS.md](../../../AGENTS.md)を正とする。
6. 一度に進める実装テーマを絞る。パス変更と性能・機能変更は分け、検証できる単位にする。
