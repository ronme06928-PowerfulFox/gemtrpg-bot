# リポジトリ構成整理計画

作成日: 2026-10-31
進捗は[課題一覧](backlog.md)。この計画の作成時点では、実ファイルの移動・削除・import変更を行わない。

2026-10-31に[初回棚卸し](repository_inventory.md)を実施した。追跡860ファイルの分類、起動・ビルド・データの参照経路、整理候補と未確認事項を同文書に記録している。段階2以降ではこの結果を基準に、対象ごとに配置と検証範囲を具体化する。

## 目的

積み上がったファイルの用途・責務・生成元を追いやすくし、機能追加・不具合調査・ビルド・運用を安全に進められる配置へ整理する。見た目の整列だけでなく、正本・生成物・実データ・一時出力の区別を明確にする。

## 入口資料の統合

`REPO-DOCS`では、ルートREADMEを開発・運用の短い入口として新設する。`readme.txt`の起動・更新コマンドはREADMEへ、`RENDER_SETUP.md`の設定と障害調査の要点はF01 Part 3へ、`task.md`の盤面操作・表示の現行仕様はE01へ統合する。旧文書の過去の値やファイル名は現行コードへ照合し、重複するチェックリストや未確認の「修正済み」説明は現行仕様としてコピーしない。

統合先と参照を確認した後、重複する旧3文書を削除する。棚卸しは調査当時の記録として残し、削除済み文書への実リンクは現行の正本へ付け替える。アプリの機能・設定・パス、本番のStart Command、ビルド成果物は変更しない。入口の不一致は `REPO-ENTRYPOINT` に残す。

受け入れ条件は、起動・更新・ビルド・テスト・規約・常設課題への導線があること、統合内容をコードと照合できること、旧ファイルへの現行リンクが残らないこと、文字・リンク・差分検査が成功すること。文書のみの変更のため、実装テストは追加しない。

統合先は[ルートREADME](../../../README.md)、[F01 Part 3](../../implemented/F01_Operations_Manual.md#part-3-renderデプロイ運用手順)、[E01 §4.4](../../implemented/E01_Visual_Battle_Architecture.md#44-盤面の自由移動トークン対象選択)。実施結果と検証は課題一覧に残す。

## テスト出力と履歴資料の整理

`REPO-OUTPUTS`のうち、まず `tests/test_seq_simple.py` と `tests/test_sequential_effects.py` の重複する検証を、後者のpytestテストへ統合する。前者はルートの `test_results.txt` を毎回作り、両方ともFAIL文字列を表示するだけでassertがない。保存済みの結果には初期3・2・8のままの値とFAILが記録されている。

現行の `process_skill_effects` は、効果を仮想状態へ順に適用して後続の条件を評価し、実状態を変更する命令の一覧を返す。呼出し元が命令を反映する前に実キャラクターの変更を期待しない。アプリ側のこの契約は変更しない。

テストの入力は初期破裂3・2・8と、無条件の+5、続く「8以上なら+5」の2効果。`states`リスト形式と旧テストの直下フィールド形式の両方について、変更命令の件数・対象・内容、反映後の値13・7・18、入力が未変更であることをassertする。実処理・ルール・スキルデータを変更せず、重複するデバッグテストと再生成結果を削除する。

削除前に隔離した作業ディレクトリで出力生成を再現し、統合後も隔離実行でpytest成功と作業場所にファイルを残さないことを確認する。関連する効果処理テスト、構文、文字、文書リンクと差分を検査する。

履歴資料は別の判断として扱う。`output/pdf/`のレビューPDF22本は合計5,696,034 bytesで、出版物のREADMEがGit管理を指定している。`logs/migration_v2/`の4 JSONは合計239,362 bytesの過去記録、ルートの `error.log` は2,258 bytesのUTF-16の例外ログである。2026-10-31のユーザー選択1により、この27本はすべて現在の場所とGit管理のまま保持する。配信用PDF・原稿・マスター・実データも保持する。

## 共通処理と入口の依存分離

`REPO-BOUNDARIES`では次の2点を実施する。現在のAPI入出力・エラー形式・CLI終了コード・マスター・キャラクター生成・状態更新は変更しない。

| 共通処理の所在 | 変更後 | 呼出し元 |
|---|---|---|
| `scripts/skill_catalog_tool.py`の `load_skills`・`lint_catalog`と埋込制約の検査 | `manager/skill_catalog_validation.py`へ集約。CLIには引数・レポート・任意WARNを残す | `manager/data_manager.py`とCLIが同じ検証コアを利用する |
| `events/battle_only/runtime_builders.py` | 全体を `manager/battle_only_runtime.py`へ移し、旧モジュールは削除する | Socket入口と `manager/sim/preset_loader.py` が共通モジュールを利用する |

移動する関数はASTでも前後を比較し、計算・乱数・時刻・命名・初期化の条件を保つ。旧パス用の互換ファイルや重複実装は作らない。現在のCLIコマンドとSocketイベント名はそのままとする。

先に、マスター更新がCLIをimportせずに検証することと、シミュレータのプリセット構築がSocket入口・appをimportせずに使えることをテストし、現在の依存経路で失敗することを確認する。既存のlint・CLI・更新フック・戦闘専用・シミュレータ関連を実行した後、状態生成の共有処理を動かすため全件テストも確認する。関連資料と未実装計画の参照先を更新する。

## 起動入口の統一

## マスターJSONの読込先の統一

`REPO-CACHE-PATHS`では `manager/cache_paths.py` のルート旧配置へのフォールバック・自動コピー・旧パス定数を削除し、呼出し元とテストを `data/cache/` の指定へそろえる。2026-10-31の確認では対象8 JSONはすべて同フォルダに存在し、ルートに同名ファイルはない。JSON自体の内容・配置・Git管理は変更しない。

`load_json_cache(path)` は指定ファイルのJSONを返し、不在なら `None`、壊れたJSONなら従来どおり例外とする。読込時にファイルを作成しない。ローダー側の欠落・空データ時の再取得やエラー処理、明示更新による保存は維持する。旧プリセットの手動エクスポート入口は `data/cache/battle_only_presets_cache.json` を読む役割のまま保持する。

先に、旧配置に同名JSONがあっても不足キャッシュとして扱い、自動コピーしないことをローダー経由で検証する。通常読込・欠落・不正JSON・明示保存を一時フォルダで検証し、関連テストと全件テストで他ローダーへの影響を確認する。旧ローカルのDB・ルームJSON・`data/images.json`の保持判断は本作業に含めない。

## 旧保存データの保全退避

## 段階2: 配置と責務の案

下表は整理の方向であり、アプリ全体を `src/` へ移すなどの最終構成を決めたものではない。棚卸し後に、効果と変更量を比較して具体的なパスを定める。

| 区分 | 整理の方向 |
|---|---|
| ルート | 起動・依存・ビルド・共通規約など、ルートにある理由を説明できるものを残す。開発者向けREADMEの必要性も検討 |
| バックエンド | 入口、ドメイン処理、状態・保存、外部サービス処理の責務を明確にする。機械的な一括移動を避ける |
| フロントエンド | `static/js/`・`static/css/` のソースと `static/dist/` の成果物を区別。依存順とURLを同時に管理 |
| データ | 起動に必要なマスター、ルーム等の実データ、検証データを分ける。永続化先は現行仕様を確認してから決める |
| スクリプト・テスト | 継続利用する検査は `scripts/`、自動テストは `tests/`。一度きりの調査出力を混ぜない |
| 資料 | 実装仕様はA〜F、運用手順は `operations/`、機能計画は `planned/`、常設活動は `projects/`。重複説明は正本へ寄せる |
| 書籍・動画 | 制作用ソースと公開・確認用出力を区別。アプリ配信と製本・動画ビルドの参照を守る |
| ローカル出力 | 既存の `_local/` など、AGENTS.mdで定めた置き場へ寄せる。保持範囲と再生成方法を明記 |

## 段階3: 小さく実施する

推奨分割は「入口・古い説明の統合」「確認済み出力の整理」「独立したスクリプト群」「参照範囲の狭いモジュール群」「責務分割を伴う本体整理」。順番と対象は棚卸しで決め、全項目を必須にはしない。

- 移動先・全参照・検証を資料に先に定義する。挙動を伴う変更は期待する契約をテストへ追加してから実装する。
- 移動だけなら既存テストと経路の検証を使い、ファイル名だけを固定する形式的なテストは増やさない。
- import、Flaskのルート・静的パス、ビルド順、プラグイン探索、設定、テスト、CI、資料を同じ変更単位で整合させる。
- `__file__` 相対パス・作業ディレクトリ・WindowsとRenderのパス大小文字を確認する。互換用の旧パス・旧モジュールを残す設計は行わない。
- JS/CSS・ビルド構成の変更は `npm run build` と成果物更新を含める。RenderにNodeがない前提を守る。
- データ格納先を変える場合は、既存データをどう保持・利用するかを先に明確にする。後方互換・データ移行コードを追加しない方針と、唯一のデータを不用意に消さないことを両立する。
- 別セッションの未コミット変更と使用中の出力は対象から外し、その作業者に整理を任せる。

## 削除・出力整理

削除前に中身・生成元・参照・唯一性・利用者を確認する。Gitにない唯一の成果物は、必要な正本として適切な場所へ保全してから整理する。秘密情報はGitに追加しない。

`static/dist/`、配布・配信に必要なPDF、マスターJSON、書籍のフォント・動画の音声キャッシュは、名前だけで不要物と判断しない。作業完了時には、削除・再配置した対象、残したもの、再生成方法を報告する。

## 検証と受け入れ条件

1. 整理対象ごとの用途、保持理由、参照元、移動先が資料から追える。
2. 関連テスト、必要なビルド、ルート・import・配信・起動の確認が成功する。本体の広い変更では全件テストを実施する。
3. 旧パスの検索結果を確認し、残る参照が意図した記録・対象外であることを説明できる。
4. エンコーディング・文字化け・差分を検査し、動作変更や無関係な整形を混ぜていない。
5. 実機確認用の出力を整理し、正本・必要な成果物・実データを保持している。
