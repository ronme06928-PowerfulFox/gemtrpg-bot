# 安定運用・復旧計画

作成日: 2026-10-31
進捗は[課題一覧](backlog.md)。実際の運用手順の正本は [F01](../../implemented/F01_Operations_Manual.md) と [operations](../../operations/account_system_deploy_runbook.md) を用い、確認・整備した内容を反映する。

## 目的

一時切断、保存失敗、再起動、デプロイがあっても、状態を確かめてセッションへ戻れるようにする。速度改善で保存や同期の正しさを崩さず、異常時に原因と復旧方法を追える土台を用意する。

## 現在の前提と未確認点

- `active_room_states` が状態の正で、DB保存は約2秒単位に集約される。この間にプロセスを失った場合の未保存範囲と、シャットダウン時の保存実態を確認する。
- 本番はPostgreSQL、ローカルはSQLite。Renderのローカルファイルを永続保存先として扱わない。
- 現行のフロントエンドは切断時に通知してページを再読み込みする。再接続時の状態・操作・解決表示の扱いは改善候補。
- `/healthz` はDB・外部APIに触れない軽量な生存確認。200応答だけでは保存やSocketの正常性を確認できない。
- Neon画面で履歴6時間・スナップショット0件・定期設定なしを確認し、11/1にユーザーが初回のPCバックアップを取得した。[取得と検査の手順・記録](../../operations/postgres_backup_runbook.md)を参照。本番の取得分の実DB復元、保存・接続エラーの頻度、許容するデータ損失と復旧時間は未確認。

根拠: [アプリ](../../../app.py)、[ルーム管理](../../../manager/room_manager.py)、[フロントの接続処理](../../../static/js/main.js)、[AGENTS.md](../../../AGENTS.md)。

## 調査・実施する内容

| テーマ | 調査と改善候補 | 受け入れ条件 |
|---|---|---|
| 保存と復元 | メモリ更新・通知・保存要求・DB反映・再起動後の復元を追う。保存失敗と再試行・終了時保存を確認 | 正常系・保存失敗・終了途中を検証し、成功と未保存を区別できる |
| バックアップ | 保存対象、サービスの保持期間、取得と復元、外部画像との関係を確認する | 非本番で復元を試し、必要な設定・所要時間・復元できない範囲を記録する |
| 再接続 | 一時切断を表示し、接続復帰→再入室・権限確認→全体再同期→操作再開を設計する | 古い状態を操作可能にせず、重複適用や意図しない自動再送を防ぎ、複数端末で復帰できる |
| 重複・順序 | 通知・操作のIDとrevision、応答待ち・タイムアウト・拒否時の扱いを確認する | 二重送信・順序違い・古い応答・再接続後でも結果が一致する |
| 観測 | 既存のHTTP計測を活かし、Socket操作、保存失敗、遅い処理、再接続を必要な粒度で追う | 問題の操作と段階を追え、秘密情報を残さず、計測負荷を許容できる |
| デプロイ | 本番設定、ビルド成果物、依存固定、起動・終了、公開中の接続と保存への影響を確認する | 変更単位に必要な検証と、異常時の復旧手順が明確になる |

## 実施順と検証

1. まず `OPS-RECOVERY` で現在の保存・バックアップ・復元を確認する。既存のテストと運用資料を読み、足りない検証を特定する。
2. 再接続の改善は `PERF-PAYLOAD` と状態同期の契約を共有する。表示だけの復帰とサーバー状態の復帰を混同しない。
3. 追加する監視は必要性を確認して絞る。軽量な生存確認とは別に、DBやSocketを確認する方法と頻度を検討し、重い確認を `/healthz` に詰め込まない。
4. 障害・バックアップ復元の試験は非本番で行い、ユーザーの実データと本番接続を壊して試さない。認証情報・接続URL・バックアップ本体を文書やGitに載せない。
5. 実装変更では失敗・重複・順序違いを含むテストを先に追加する。SQLiteとPostgreSQL、threadingとeventletの違いも対象に応じて確認する。

推奨する変更単位は「復旧の現状記録・手順整備」「不足する失敗ケースの検証と修正」「再接続」「観測の補強」。単一変更にすべてを混ぜない。

## ローカル保存・復元の検証

`OPS-RECOVERY-LOCAL`ではテスト用の一時ディレクトリにSQLiteを作り、現役の `instance/`・本番DB・旧保存データを使用しない。外部データ取得は起動せず、factoryへテスト用DB URLを明示する。テスト用のユーザー・ルーム・キャラクター・宣言・ログのみを用いる。

先にF01 Part 7の保存契約を更新し、次をテストする。

- 約2秒の保存集約で最新状態が実DBへ反映され、別プロセスが復元できる。
- デバウンス待ち中に正常終了してもatexitが最新状態を保存する。終了時は進行中の保存を待ち、最初の失敗を含めて最大2回試す。
- DB存在確認での例外を不存在と誤認せず、rollback後に再試行する。
- 再試行上限後も未保存状態を保持し、定期的な無限再試行は行わない。次の保存要求・明示フラッシュ・正常終了で再試行する。実際に削除されたルームは復活させない。
- 強制終了ではatexitが走らず、未コミットの最新操作が復元されないことを、最後に保存済みの状態との違いで確認する。
- SQLiteのオンラインバックアップから別の一時DBを復元し、ルーム・所有者・権限・履歴ログを確認する。これを本番PostgreSQLのバックアップ確認済みという扱いにはしない。

通常保存の2秒と自動再試行1回は維持し、同期保存化・画面通知・新しい監視・本番設定変更は行わない。運用手順は[保存・復元確認手順](../../operations/persistence_recovery_runbook.md)を正本とし、検証結果は課題一覧に残す。

## 運用方針として決めること

- 許容できる未保存時間と復旧時間。全操作を同期保存するかは、応答時間との比較で判断する。
- 現契約のバックアップで足りるか、取得先と追加費用をどうするか。
- 保存失敗・長い切断を、誰に・どのタイミングで知らせるか。
- セッション中のデプロイをどう扱うか、異常時の復旧判断と手順。

これらは要調査・未決定であり、新しい通知サービス・定期ジョブ・有料契約をこの計画だけで設定しない。
